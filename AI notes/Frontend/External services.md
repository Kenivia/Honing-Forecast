# External services

The app is a static site with no backend of its own. Everything external goes through one Cloudflare Worker.

Character import can also go through lostark.bible's OAuth API when the user signs in (optional; scraping stays the default): `lostark.bible OAuth API.md`.

## The Worker

`cloudflare/worker.js`, deployed separately with `pnpm cloudflare-deploy`. Its URL reaches the frontend through `VITE_WORKER_URL`: `https://api.honing-forecast.com` since 2026-11-24, a custom domain (`routes` in `wrangler.toml`), so the zone's WAF runs before it. The old `snowy-base-1817.kenivia-fan.workers.dev` stays on (`workers_dev = true`, which must be written out: a custom domain in `routes` turns workers.dev off by default) until old clients have moved; workers.dev bypasses the WAF, so turn it off then. Upstream requests carry `Referer: https://honing-forecast.com/` (lostark.bible confirmed it is covered). It does two things as a caching proxy:

- forwards market price requests to loa-buddy's market data API (`GET /market/<region>?items=<slugs>`; the Worker POSTs the body upstream). The site now uses `GET /prices/<region>?items=<slugs>` instead (Market prices, below); `/market` stays for older clients;
- fetches character pages from lostark.bible, which the browser cannot call directly (`GET /character/<region>/<name>/<suffix>`).

It holds no application logic for those two; parsing happens in the frontend. The one exception is the analytics route below.

- **Cache**: Workers Cache (`[cache] enabled = true`), not KV. It caches the Worker's own GET responses by path and query, for as long as their `Cache-Control` says: `reply()` sends `public, max-age=3600` on 200s and `no-store` on everything else. A hit never runs the Worker (no CPU, no upstream fetch, no rate-limit row) but still counts as a request toward the free plan's 100k/day. Works on workers.dev on the free plan, keeps the CORS headers on hits. Per Worker version, so a deploy empties it; not emulated by `wrangler dev`.
- **Rate limits**: per source, per minute, global: market 10, lostark.bible 200 (character pages and upload raids together). `allow()` is one upsert on the D1 table `limits` (one row per source) that returns nothing once the minute's cap is reached. Only cache misses reach it. An allowed fetch costs 1 D1 row write, a refused one 0 (verified on D1), so lostark.bible held at its cap all day would pass the free plan's daily D1 write limit: accepted, it fails closed (D1 errors refuse the fetch). Refused: `429 Rate limited` for the proxies.
- **Per-IP limits** (since 2026-11-24): `ROUTE_LIMITS` at the top of `worker.js` maps routes to Workers Rate Limiting bindings, whose numbers are the `[[ratelimits]]` blocks at the top of `wrangler.toml` (one `namespace_id` each, so counters are separate): `GET /character|/bible` 60/min (roster import fetches up to 60 a minute, `fetch_uwuowo`), `GET /market|/prices` 30/min, `POST /snapshots` and `POST /moves` 5/min each, keyed by `CF-Connecting-IP`; refused with `429 Too many requests`. Loopback calls carry no IP and are not limited; `/scans` is not limited. They keep one client from using up the global caps above or filling D1; they do not save the 100k requests a day (a limited request is already a Worker invocation). Only the zone's WAF rate limiting rule (the user's, dashboard; free plan: one rule, Path only, 10 s window, so it covers the Pages site too) blocks before the Worker, and only on the custom domain. Works under `wrangler dev --local` (the 6th `/moves`, the 31st `/prices` refused), but deployed it never refused (80 `/prices` misses in 40 s from one IP, `limit()` logged `success: true` each time; workers-sdk issue 16097).

## Analytics uploads

The budget snapshots (`Screen scanner/Manifest.md`) are uploaded so the author can study income across players. They carry each character's tier and upgrade grids and the characters' gear levels as lostark.bible has them, at upload and again a day after each export (older uploads lack some of these). Opt-out: `analytics` in the roster config (global, saved, on by default), the "Share owned material anonymously" checkbox, last in the scanner page's sidebar (`ScannerControlPanel.vue`), its tooltip saying what is sent, that names are used for the lostark.bible lookups and kept until the follow-up.

- **Frontend** (`Utils/Analytics.ts`, `upload_snapshots`): production and dev builds (dev ones send version `"dev"`, so they can be told apart), only when `MODE` is `production` or `development`, so never under Vitest (`test`) or the node suites (esbuild defines `import.meta.env` as `{}`), nor under browser automation (`navigator.webdriver`, which keeps the e2e tests, on a dev server pointed at the real Worker, from uploading). `App.vue` calls it on load and whenever the number of snapshots or the flag changes. Per roster, the snapshots without `sent`, oldest first, up to 20 per request and under 300 KB of body (a snapshot too large on its own is marked `sent` and skipped) (`POST /snapshots`: roster id, region, `LATEST_VERSION`, the snapshots as stored, names included); each batch is marked `sent` once the Worker answers ok. A failure stops until the next trigger, so nothing is lost but a closed tab can send a batch twice: dedupe when analysing (below). Existing snapshots are back-filled the same way. One upload at a time.
- **Worker** (`handleSnapshots`): rejects bodies over 300 KB, takes each character's latest name across the batch and **deletes every name** from the snapshots, fetches each character's logs from lostark.bible (`/character/<NA|CE>/<name>/logs/__data.json`, SvelteKit's data endpoint, decoded with `devalue`'s `unflatten`; a capped number of characters) together with its gear (below) through a loopback call to its own `GET /bible/<NA|CE>/<name>` (`lookUp`, `ctx.exports.default.fetch`; cached only when neither half is a passing failure), so Workers Cache serves a character looked up within the hour; each loopback call is its own invocation with its own 50-subrequest budget, but is billed as a request, and inserts one row into D1. A log is cut down to `{boss, difficulty, isBus, gearScore (floored), class, week}`, `week` being the start of its weekly reset (Thursday 10:00 UTC): the log id, name, exact time and dps numbers would let anyone find the character again on lostark.bible. Instead of logs a character gets a reason: "no name" (`Newchar…` defaults), "no region" (Custom), "not found", "private" (these and logs are cached), "error …", "rate limited" (not cached; that upload loses the character's raids). The page only lists the last 25 logs, so overlapping uploads are what builds a history; names typed by hand that are not the in-game name fetch someone else's or nothing.
- **Gear** (`fetchGear`, the `gear` column, same reasons as raids): `/character/<NA|CE>/<name>/__data.json`. lostark.bible has no live equipment list: it keeps one loadout per kind of content the character last entered (`most_recent_raid`, `most_recent_chaos_dungeon`), each with its `lastUpdated`, so an upgrade shows only after the next raid or chaos dungeon. The page itself refreshes every hour or two (`header.lastRefreshTime`, and its item level, which can run ahead of a stale loadout's). Kept: `{ilvl, refreshed, loadouts: [{kind, updated, ilvl, items: [{slot, id, honing, adv}]}]}`, times floored to the hour, item levels exact; items are the six pieces and `bracer` (the vambrace); ids tell the tier (T4 13461xxxx, Serca 13462xxxx). A character with no loadouts is "not found".
- **Follow-ups**: export snapshots carry `by`, the exported character (`Manifest.md`, "Snapshots"). Each upload upserts a `pending` row per exporter with a valid name and region (char id, roster, region, version, **name**, due = now + 24h), so each character has its own timer and every export pushes it back; Manual snapshots and older clients start none. An hourly Cron Trigger (`[triggers]` in `wrangler.toml`, `scheduled` -> `followUp`) takes a capped batch of due rows, looks them up through the same loopback (`ctx.exports` works in the cron handler: works on `wrangler dev --test-scheduled`, `/__scheduled`), stores one `uploads` row per roster with version `followup <version>` and no snapshots, and deletes the rows unless rate limited or pushed back meanwhile (`DELETE ... WHERE due = <the due read>`). Names are kept only in `pending`, until then. The upload's own row keeps the lookup at upload time, so both stay for a before/after.
- **D1** `hf-analytics`, binding `DB`, tables `uploads`, `pending` (above) and `limits` (`cloudflare/schema.sql`; `uploads`: id (`AUTOINCREMENT`, so never reused after a pull empties the table; unique across pull files), received, roster, region, version, snapshots, raids and gear as JSON text; a remote table made before `gear` needs `ALTER TABLE`). Only the account can read it: the Worker's routes only write `uploads`.
- **Pulling**: `pnpm pull-analytics` (`scripts/pull-analytics.mjs`) takes the highest id, pages everything up to it into `ignored/analytics/uploads-<time>.json` (rows with `snapshots`, `raids` and `gear` parsed, `gear` null on older rows), then deletes up to that id. `--keep` skips the delete, `--local` reads `wrangler dev`'s local database. Each wrangler call is retried up to 3 times: right after wrangler refreshes its OAuth token (it expires hourly) the first D1 call is sometimes refused with 403 (seen in wrangler's own logs, `%APPDATA%/xdg.config/.wrangler/logs`).
- **Analysing**: `scripts/analytics/` (Python, pandas + matplotlib), run from that folder after a pull. Raw data and figures stay in `ignored/analytics/` (gitignored).
  - `load.py`: `load()` reads every pull file into DataFrames: `snaps` (one row per snapshot, `by` the exporter), `mats` (long form: roster, char, band `roster`/`tradable`/`bound`/`special`, label, amount, `gold` at that snapshot's own prices; Silver has no price; `disabled`, for bound rows from the snapshot's flag, so always False for older uploads; `tier`, the character's, on its rows), `chests`, `raids` (logs, deduped across uploads, plus one row per character with a reason instead). `gear` (one row per item per loadout per lookup, `followup` true on follow-up rows, or one row with the reason). Drops `dev` uploads and their follow-ups unless `--dev`. Dedupes snapshots by content without `roster_id`: one pre-uuid save migrated in two places (`migrate_9_to_10`) uploads the same snapshots and char ids under two roster ids, so roster and `at` are not enough.
  - `check.py`: sanity report (duplicates, names left in, raid log keys, tier/grid coverage, rosters with no logs, capped or huge amounts, client clock skew). Run it first on every pull.
  - `plot.py [uploads|materials|raids|all] [--roster <prefix>] [--bands bound,roster,tradable]`: PNGs into `ignored/analytics/figures/`. Each plot returns `(figure, table or None)`; `raids` prints the boss table.
  - `materials`: one row per character whose own exports span `MIN_DAYS`, three panels (main 7 plus special leaps in the site's colours, optional weapon, optional armour in arbitrary fixed colours, the character's tier's labels only), amounts summed over the chosen bands (a band missing from a snapshot takes its nearest known amounts, previous else next; a missing label stays zero since exports drop zeros) and drawn as % of each line's first non-zero value, one point per day, split at the 10:00 UTC daily reset: the latest of the roster's "After export" snapshots that hold the character (bigger on days it exported; honing marks snap to their day). Daily points, because bursts of exports minutes apart are scan coverage growing, not income, and spiked the lines. Dotted lines are honing from the gear lookups (`honing_events`: a slot's level passing its highest so far in the most recent loadout; the item id changes at vambrace +10 to +15, so a higher level on a new id counts and a lower one restarts the slot). Rows with no honing in their window ("clean", so pure income) come first, then by span.
  - `app.py`: Streamlit page showing every plot in `PLOTS` with its table; the sidebar picks the bands `materials` sums. `pnpm analytics` pulls first (so it deletes the pulled rows like `pull-analytics`), then serves it (`python -m streamlit`: the `streamlit` executable is not on PATH).
  - **Reading the data**: users export once per character in a row, minutes apart, so consecutive "After export" snapshots mostly show scan coverage growing and materials moving between bands, not income; income needs diffs across sessions (hours or days apart, `hours` in `diffs`). Typed placeholders exist (Silver at the old cell cap, a whole roster of 99,999 / 999,999 cells): filter them before averaging.
  - **Tying spending to upgrades**: only scan-to-scan changes ("After export" to a later "After export" of the same character) are what the game shows; "After" to the next "Before" is the app's own auto-deduction and hand edits. A Want to FetchedDone flip can come from a lostark.bible fetch with no spending at all. Roster-bound and tradable stock is shared, so the roster's other characters must not have upgraded in the same window. Shards and gold are currencies and keep their saved value when not read. A check that works: per material, (decrease minus unlock cost) / expected tap cost should come out one factor (taps relative to expected); armour and weapon apart, since Blue is armour-only and Red weapon-only in Serca. A material the character has disabled (the default for Shards) is not deducted; uploads say so in `disabled` (`Manifest.md`, "Snapshots").
- **Testing**: the deployed Worker is whitelisted by lostark.bible (Workers are blocked by default), the logs endpoint included. `wrangler dev --local` runs the route against a local D1 (keyed by `database_id`; apply the schema with `d1 execute --local --file`), but lostark.bible answers 403 to it, the character proxy included, so raids come back as "error 403" there. Point a dev server at it with `VITE_WORKER_URL=http://localhost:8788 npx vite --port <p>`; a Playwright-driven page needs `navigator.webdriver` overridden in an init script to upload at all.

## Market scanner passes

The native market scanner (`Market scanner/Overview.md`) posts each pass to the Worker; the site reads each material's lowest listing through `/prices` (below), and the market page's Gems tab reads `sections.gem` of `GET /scans/latest/<region>` (`GemDataFetcher.ts`, kept in memory for a minute per region, NAE and EUC only).

- `POST /scans`, only with `Authorization: Bearer <MARKET_TOKEN>` (a Worker secret; locally `cloudflare/.dev.vars`, gitignored; compared with `timingSafeEqual`). The body (up to 1 MB) is stored whole in D1 `market_scans`, one row per pass, once per region and `started` (a resend answers "stored before"). Its `points` [key, day, value] are merged into `market_history`, one row per region and month (`{key: {day: value}}`, a later value for a key and day wins), in the same batch as the pass. So is `market_latest`, one row per region, `{slug: [price, at]}`: each material's lowest listing (`depth[0]`) by loa-buddy's slug of its name (`slug()`: lower case, apostrophes dropped, other runs of non-alphanumerics to `-`), where its `at` is newer than the one kept, so it is the newest reading of each item over every pass.
- `GET /scans/latest/<region>`, `GET /scans/<id>`: `{id, received, scan}`, the pass as posted. `GET /scans/history/<region>/<yyyy-mm>`: that month's `{key: {day: value}}`, `{}` when none.
- **Not cached** except a pass by id (it never changes): each read is one indexed row, so a request costs one D1 row read whether or not it is cached, and Workers Cache hits count toward the 100k requests a day anyway. History is a row per month, not per day or point, for the same reason, and to keep each row's JSON small for the 10 ms CPU limit.

## Market prices

`Utils/MarketDataFetcher.ts`.

- **One consolidated source**: `GET /prices/<region>?items=<slugs>` on the Worker fetches loa-buddy upstream (the `market` rate limit) and reads `market_latest` together, and per item returns whichever is newer, as loa-buddy's own rows plus a source: `[{item_slug, price, timestamp (s), source: "loa-buddy" | "hf"}]`. Either source failing leaves the other; both failing is a 502. Cached 60 s (`PRICES_CACHE`) so new passes show quickly: at most about one upstream fetch and one D1 read per region and item list a minute.
- The market page shows, under each price (below the bundle size), how old the fetched price is ("just now", "N mins ago", "N hours ago", "N days ago"), with a hover naming its source (loa-buddy, linked, or Honing Forecast). It is decided by value alone: the price equals the saved response's price for that bundle (`parse_sources`; rows saved before `/prices` have no `source` and are loa-buddy's), else "Default fallback" when it equals the region's default (`default_prices`; Custom's are 0 and Gold 1), else "Manual". Gold and Silver have none.
- Prices are fetched per region on app load. A region set to custom is never fetched, and one global `auto_fetch` flag can turn fetching off (the fetch button still forces one).
- The raw response is kept in the store (and therefore in localStorage) with its timestamp and reused for a minute (the Worker's cache time), across reloads too. A forced fetch only reuses a response under a second old. A failed fetch applies the saved response, however old.
- Item slugs from the API are mapped onto bundle keys. A fetch writes only the bundles the response lists, so anything the market does not sell (Silver, Gold, special leaps, and any book neither source lists yet) keeps whatever the user typed; fallback prices are only the column's defaults. A price typed for a listed item is a temporary override: the next fetch, or the cached response re-applied on load, replaces it, and the market page's sidebar says so. Custom is the region for prices of one's own.
- Shards are sold in bags of several sizes; after each fetch the cheapest per shard is selected.
- The fetch flags (`is_fetching`, `market_fetch_failed` in the runtime store) are per region, so regions fetch in parallel and the market page shows the selected region's status.
- Serca prices are not synced with T4: the market page only shows an effective price, the cheaper of buying and converting (`effective_unit_prices`).

## Character import ("Uwuowo")

`Components/Common/Uwuowo`. The name is historical; the source is lostark.bible.

- Two paths behind `fetch_char` / `fetch_roster` (`UwuowoUtils.ts`): signed in (`Utils/BibleAuth.ts`) and the character is in one of the user's linked rosters (same region, `norm_name`: transliterated to ASCII with `@sindresorhus/transliterate`, lower case, so a typed "Elsa" finds "Ëlsa"; an exact name wins first, since a roster can hold both an accented name and its plain form: `match_name`) → OAuth API; anything else, or any API error → the scraping below. Other people's characters always scrape.
- API path: the roster list is the linked roster's names; a character is its newest loadout (`loadouts_to_result`): slots `head, shoulder, upper_body, lower_body, hand, weapon` + `bracer` (vambrace, +0 if absent), tier from the item id (Serca `13462xxxx`), `adv` from `advancedHoning` on T4, per-piece item level NaN (blank in the confirm panel), item level and class from the rosters entry. The API's class ids (`berserker_female`, `dragon_knight`) are mapped to the names the site shows (`BIBLE_CLASSES`: Slayer, Guardianknight), the same names the scrape reads.

- The Worker returns the site's HTML and the frontend scrapes it by DOM position. This breaks whenever the site changes its markup, and should be assumed fragile. Equipment is read from the first 12 cells of the equipment grid (armor alternating with accessories); the grid has extra cells after them (Vambrace, Orb). The vambrace cell is found by its "Vambrace" label (top row `Vambrace, +N, T4`, no item level) and becomes a 7th piece (Serca, item level NaN); without one (empty cell or "Not Equipped") it is +0.
- The vambrace never decides the tier and is applied only when the import ends up Serca (fetched-done up to +N, its wants kept); on T4 its row is left alone, and `upgrade_info` (`PayloadBuilder.ts`) drops T4 vambrace upgrades anyway.
- A successful import saves the character's class (`class_name`, the display name; the `apply` callbacks carry it as their last argument, `ApplyFetch`), marks already-completed upgrades in the tickbox grids as fetched (optionally locked), may switch the character's tier, and seeds advanced-honing progress.
- Advanced progress is seeded as `adv_progress[0] = (level % 10) * 10`, the unit AdvancedDetails and Rust use (10 per level within a block of 10, 100 when done).
- **Signed in** (`Utils/BibleSync.ts`):
  - A linked character's fetch button becomes "Last fetched <time ago>" (`useTimeAgo` on the profile's `fetched_at`, "never" at 0) plus a refresh icon (`rotate-right-solid-full.svg`, spinning while it works). `refresh_char` applies without the confirm panel; a failure shows under it. Renaming a linked character refreshes instead of opening the popup. Unlinked characters and signed-out users keep the old button and popup.
  - A linked character's name and region are locked (`linked` computed in `Uwuowo.vue`, passed as `locked` to `CharNameInput` / `RegionSelector`): a read-only input and disabled select styled as plain text, same size. On Roster setup, a roster with any linked character shows "Your roster on lostark.bible" in its header (header shown even for a lone character) and its region is locked. Signing out unlocks everything.
  - Refresh and auto-refresh use `apply_results`' `keep_tier`: switch to Serca only when all six pieces are Serca, otherwise keep the character's tier. The manual popup keeps its own rule (any Serca piece, or "force T4").
  - **Linked rosters change** on lostark.bible (link / unlink). The `/rosters` list lives in `bible_rosters` (shallowRef, `BibleAuth.ts`): loaded on first use, cleared on sign-in / sign-out / 401, refetched by Sync (`linked_rosters(true)`) and after any failed API character fetch. Otherwise a page reload picks up changes (no focus/interval refetch, by choice). UI lock checks use the reactive `linked_now`; async callers use `find_linked`. Unlinking only unlocks and switches those characters to scraping; nothing is deleted.
  - **Auto-refresh**: once per launch (`App.vue`), every character fetched before (`fetched_at > 0`, or a `class_name`, which imports from before `fetched_at` left) in a linked roster, one at a time. It never adds or renames.
  - **Sync** (`sync_rosters`): after sign-in (`AuthCallback.vue`, once back on the page) and from "Sync with lostark.bible" on Roster setup. Each bible roster goes to the local roster of its region with most `norm_name` matches (Custom ignored; exact names are matched across all bible rosters before accentless ones, and each local character matches once); matches are renamed to the exact bible name. No match: a new roster with all its characters. Characters matched in another local roster stay there (no merges). If the chosen roster still has unmatched local characters and the bible roster unmatched names, `BibleSyncPopup.vue` (in `App.vue`) lets the user pair them (picking renames) or leave them; Confirm adds the leftover bible names, Skip or closing adds nothing to that roster. A lone unfetched `Newchar*` is replaced only while untouched (grids, budgets, chests and its roster's mats equal the defaults, compared as JSON; `untouched` in `BibleSync.ts`). Names set by sync, the popup and Fetch remaining go through `format_char_name`, unique per region, so an NA and a CE `Bob` both stay `Bob` (the route carries the region). Nothing about the match is saved: renames make the next sync match by itself. Then every matched and added character is refreshed.
- Roster import fetches the roster list, then each missing character in turn (missing: no exact local name, and no accentless one unless another roster name shares those letters), under a client-side rate limit of 60 requests per rolling minute (`fetch_uwuowo`). A result that lands after the name or region changed is dropped, and a character fetch never runs without a region (custom).

## Changelogs

Markdown files in `public/change-logs`, one per version. Version names are discovered at build time; contents are fetched and rendered at runtime. `public/WIP.md` is rendered the same way as the unreleased entry and doubles as the author's roadmap. Visiting the change-log page sets the stored last-seen version to the latest, which drives a "new" marker in the footer, shown for any other version, patch bumps included (`version_equal` is plain equality). `load_change_log` (`Utils/Changelog.ts`) caches each rendered version for the session and returns null on a failed fetch, which the page shows as an error; `computedAsync` drops a fetch that lands after the version changed.
