# External services

The app is a static site with no backend of its own. Everything external goes through one Cloudflare Worker.

## The Worker

`cloudflare/worker.js`, deployed separately with `pnpm cloudflare-deploy`. Its URL reaches the frontend through `VITE_WORKER_URL`. It does two things as a caching proxy:

- forwards market price requests to a third-party market data API (`GET /market/<region>?items=<slugs>`; the Worker POSTs the body upstream);
- fetches character pages from lostark.bible, which the browser cannot call directly (`GET /character/<region>/<name>/<suffix>`).

It holds no application logic for those two; parsing happens in the frontend. The one exception is the analytics route below.

- **Cache**: Workers Cache (`[cache] enabled = true`), not KV. It caches the Worker's own GET responses by path and query, for as long as their `Cache-Control` says: `reply()` sends `public, max-age=3600` on 200s and `no-store` on everything else. A hit never runs the Worker (no CPU, no upstream fetch, no rate-limit row) but still counts as a request toward the free plan's 100k/day. Works on workers.dev on the free plan, keeps the CORS headers on hits (verified 2026-10-23 on a throwaway Worker). Per Worker version, so a deploy empties it; not emulated by `wrangler dev`.
- **Rate limits**: per source, per minute, global: market 10, lostark.bible 200 (character pages and upload raids together). `allow()` is one upsert on the D1 table `limits` (one row per source) that returns nothing once the minute's cap is reached. Only cache misses reach it. An allowed fetch costs 1 D1 row write, a refused one 0 (verified on D1), so lostark.bible held at its cap all day would use ~288k writes, past the free plan's 100k: accepted, it fails closed (D1 errors refuse the fetch). Refused: `429 Rate limited` for the proxies.

## Analytics uploads

The budget snapshots (`Screen scanner/Manifest.md`) are uploaded so the author can study income across players; since 2026-10-23 they carry each character's tier and upgrade grids (older uploads lack them), and since 2026-10-24 the characters' gear levels as lostark.bible has them, at upload and again a day after each export. Opt-out: `analytics` in the roster config (global, saved, on by default), the "Share owned material anonymously" checkbox, last in the scanner page's sidebar (`ScannerControlPanel.vue`), its tooltip saying what is sent, that names are used for the lostark.bible lookups and kept until the follow-up.

- **Frontend** (`Utils/Analytics.ts`, `upload_snapshots`): production and dev builds (dev ones send version `"dev"`, so they can be told apart), only when `MODE` is `production` or `development`, so never under Vitest (`test`) or the node suites (esbuild defines `import.meta.env` as `{}`), nor under browser automation (`navigator.webdriver`, which keeps the e2e tests, on a dev server pointed at the real Worker, from uploading). `App.vue` calls it on load and whenever the number of snapshots or the flag changes. Per roster, the snapshots without `sent`, oldest first, up to 20 per request and under 300 KB of body (a snapshot too large on its own is marked `sent` and skipped) (`POST /snapshots`: roster id, region, `LATEST_VERSION`, the snapshots as stored, names included); each batch is marked `sent` once the Worker answers ok. A failure stops until the next trigger, so nothing is lost but a closed tab can send a batch twice: dedupe when analysing (below). Existing snapshots are back-filled the same way. One upload at a time.
- **Worker** (`handleSnapshots`): rejects bodies over 300 KB, takes each character's latest name across the batch and **deletes every name** from the snapshots, fetches each character's logs from lostark.bible (`/character/<NA|CE>/<name>/logs/__data.json`, SvelteKit's data endpoint, decoded with `devalue`'s `unflatten`; at most 40 characters) together with its gear (below) through a loopback call to its own `GET /bible/<NA|CE>/<name>` (`lookUp`, `ctx.exports.default.fetch`; cached only when neither half is a passing failure), so Workers Cache serves a character looked up within the hour; each loopback call is its own invocation with its own 50-subrequest budget, but is billed as a request, and inserts one row into D1. A log is cut down to `{boss, difficulty, isBus, gearScore (floored), class, week}`, `week` being the start of its weekly reset (Thursday 10:00 UTC): the log id, name, exact time and dps numbers would let anyone find the character again on lostark.bible. Instead of logs a character gets a reason: "no name" (`Newchar…` defaults), "no region" (Custom), "not found", "private" (these and logs are cached), "error …", "rate limited" (not cached; that upload loses the character's raids). The page only lists the last 25 logs, so overlapping uploads are what builds a history; names typed by hand that are not the in-game name fetch someone else's or nothing.
- **Gear** (`fetchGear`, the `gear` column, same reasons as raids): `/character/<NA|CE>/<name>/__data.json`. lostark.bible has no live equipment list: it keeps one loadout per kind of content the character last entered (`most_recent_raid`, `most_recent_chaos_dungeon`; checked 2026-10-24), each with its `lastUpdated`, so an upgrade shows only after the next raid or chaos dungeon. The page itself refreshes every hour or two (`header.lastRefreshTime`, and its item level, which can run ahead of a stale loadout's). Kept: `{ilvl, refreshed, loadouts: [{kind, updated, ilvl, items: [{slot, id, honing, adv}]}]}`, times floored to the hour, item levels exact; items are the six pieces and `bracer` (the vambrace); ids tell the tier (T4 13461xxxx, Serca 13462xxxx). A character with no loadouts is "not found".
- **Follow-ups**: export snapshots carry `by`, the exported character (`Manifest.md`, "Snapshots"). Each upload upserts a `pending` row per exporter with a valid name and region (char id, roster, region, version, **name**, due = now + 24h), so each character has its own timer and every export pushes it back; Manual snapshots and older clients start none. An hourly Cron Trigger (`[triggers]` in `wrangler.toml`, `scheduled` -> `followUp`) takes up to 40 due rows, looks them up through the same loopback (`ctx.exports` works in the cron handler: tested on `wrangler dev --test-scheduled`, `/__scheduled`), stores one `uploads` row per roster with version `followup <version>` and no snapshots, and deletes the rows unless rate limited or pushed back meanwhile (`DELETE ... WHERE due = <the due read>`). Names are kept only in `pending`, until then. The upload's own row keeps the lookup at upload time, so both stay for a before/after.
- **D1** `hf-analytics`, binding `DB`, tables `uploads`, `pending` (above) and `limits` (`cloudflare/schema.sql`; `uploads`: id (`AUTOINCREMENT`, so never reused after a pull empties the table; unique across pull files), received, roster, region, version, snapshots, raids and gear as JSON text; `gear` was added to the remote table with `ALTER TABLE`). Only the account can read it: the Worker's routes only write `uploads`. Free plan: 100k rows written a day, 500 MB per database.
- **Pulling**: `pnpm pull-analytics` (`scripts/pull-analytics.mjs`) takes the highest id, pages everything up to it into `ignored/analytics/uploads-<time>.json` (rows with `snapshots`, `raids` and `gear` parsed, `gear` null before 2026-10-24), then deletes up to that id. `--keep` skips the delete, `--local` reads `wrangler dev`'s local database. Each wrangler call is retried up to 3 times: right after wrangler refreshes its OAuth token (it expires hourly) the first D1 call is sometimes refused with 403 (seen in wrangler's own logs, `%APPDATA%/xdg.config/.wrangler/logs`), which made the first pull of a session fail.
- **Analysing**: `scripts/analytics/` (Python, pandas + matplotlib), run from that folder after a pull. Raw data and figures stay in `ignored/analytics/` (gitignored).
  - `load.py`: `load()` reads every pull file into DataFrames: `snaps` (one row per snapshot), `mats` (long form: roster, char, band `roster`/`tradable`/`bound`/`special`, label, amount, `gold` at that snapshot's own prices; Silver has no price; `disabled`, for bound rows from the snapshot's flag, so always False for uploads before 2026-10-24), `chests`, `raids` (logs, deduped across uploads, plus one row per character with a reason instead). `gear` (one row per item per loadout per lookup, `followup` true on follow-up rows, or one row with the reason). Drops `dev` uploads and their follow-ups unless `--dev`. Dedupes snapshots by content without `roster_id`: one pre-uuid save migrated in two places (`migrate_9_to_10`) uploads the same snapshots and char ids under two roster ids, so roster and `at` are not enough.
  - `check.py`: sanity report (duplicates, names left in, raid log keys, tier/grid coverage, rosters with no logs, capped or huge amounts, client clock skew). Run it first on every pull.
  - `plot.py [uploads|holdings|diffs|raids|gearscore|all] [--roster <prefix>]`: PNGs into `ignored/analytics/figures/`. `diffs` also prints the per-label table, `raids` the boss table. Each plot returns `(figure, table or None)`.
  - `app.py`: Streamlit page showing every plot in `PLOTS` with its table, no controls yet. `pnpm analytics` pulls first (so it deletes the pulled rows like `pull-analytics`), then serves it (`python -m streamlit`: the `streamlit` executable is not on PATH).
  - **Reading the data** (first pulls, 2026-10-22/23, 20 uploads, 9 rosters): users export once per character in a row, minutes apart, so consecutive "After export" snapshots mostly show scan coverage growing and materials moving between bands, not income; income needs diffs across sessions (hours or days apart, `hours` in `diffs`). Typed placeholders exist (Silver 999,999,999 is the cell cap before 2026-10-23, so "1B or more"; a whole roster of 99,999 / 999,999 cells): filter them before averaging.
  - **Tying spending to upgrades** (looked at 2026-10-24, 106 snapshots): only scan-to-scan changes ("After export" to a later "After export" of the same character) are what the game shows; "After" to the next "Before" is the app's own auto-deduction and hand edits. A Want to FetchedDone flip can come from a lostark.bible fetch with no spending at all (the vambrace +1..+10 flips of 2026-10-23, after the vambrace fetch fix). Roster-bound and tradable stock is shared, so the roster's other characters must not have upgraded in the same window. Shards and gold are currencies and keep their saved value when not read. A check that works: per material, (decrease minus unlock cost) / expected tap cost should come out one factor (taps relative to expected); armour and weapon apart, since Blue is armour-only and Red weapon-only in Serca. The one clean case (23 Serca upgrades +16..+19, 0.55 h) gave 0.5 to 0.74 across materials. The auto-deduction there took no Shards (scan: -5.3M) because Shards were disabled for that character (the default); uploads say so only since 2026-10-24 (`disabled` in `Manifest.md`, "Snapshots").
- **Testing**: the deployed Worker is whitelisted by lostark.bible (Workers are blocked by default), the logs endpoint included; verified 2026-10-22. `wrangler dev --local` runs the route against a local D1 (keyed by `database_id`; apply the schema with `d1 execute --local --file`), but lostark.bible answers 403 to it, the character proxy included, so raids come back as "error 403" there. Point a dev server at it with `VITE_WORKER_URL=http://localhost:8788 npx vite --port <p>`; a Playwright-driven page needs `navigator.webdriver` overridden in an init script to upload at all.

## Market prices

`Utils/MarketDataFetcher.ts`.

- Prices are fetched per region on app load. A region set to custom is never fetched, and one global `auto_fetch` flag can turn fetching off (the fetch button still forces one).
- The raw response is kept in the store (and therefore in localStorage) with its timestamp and reused for a cooldown period, across reloads too. A forced fetch only reuses a response under a second old. A failed fetch applies the saved response, however old.
- Item slugs from the API are mapped onto bundle keys. A fetch writes only the bundles the response lists, so anything the market does not sell (Silver, Gold, Enhanced books, special leaps, and the Serca Tremor books, whose slugs are in the map but which the API did not list yet on 2026-10-21) keeps whatever the user typed; fallback prices are only the column's defaults. A price typed for a listed item is a temporary override: the next fetch, or the cached response re-applied on load, replaces it, and the market page's sidebar says so. Custom is the region for prices of one's own.
- Shards are sold in bags of several sizes; after each fetch the cheapest per shard is selected.
- The fetch flags (`is_fetching`, `market_fetch_failed` in the runtime store) are per region, so regions fetch in parallel and the market page shows the selected region's status.
- Serca prices are not synced with T4: the market page only shows an effective price, the cheaper of buying and converting (`effective_unit_prices`).

## Character import ("Uwuowo")

`Components/Common/Uwuowo`. The name is historical; the source is lostark.bible.

- The Worker returns the site's HTML and the frontend scrapes it by DOM position. This breaks whenever the site changes its markup, and should be assumed fragile. Equipment is read from the first 12 cells of the equipment grid (armor alternating with accessories); since 2026-10-21 the grid has extra cells after them (Vambrace, Orb). The vambrace cell is found by its "Vambrace" label (top row `Vambrace, +N, T4`, no item level; markup checked 2026-10-23) and becomes a 7th piece (Serca, item level NaN); without one (empty cell or "Not Equipped") it is +0.
- The vambrace never decides the tier and is applied only when the import ends up Serca (fetched-done up to +N, its wants kept); on T4 its row is left alone, and `upgrade_info` (`PayloadBuilder.ts`) drops T4 vambrace upgrades anyway.
- A successful import marks already-completed upgrades in the tickbox grids as fetched (optionally locked), may switch the character's tier, and seeds advanced-honing progress.
- Advanced progress is seeded as `adv_progress[0] = (level % 10) * 10`, the unit AdvancedDetails and Rust use (10 per level within a block of 10, 100 when done).
- Roster import fetches the roster list, then each missing character in turn, under a client-side rate limit of 60 requests per rolling minute (`fetch_uwuowo`). A result that lands after the name or region changed is dropped, and a character fetch never runs without a region (custom).

## Changelogs

Markdown files in `public/change-logs`, one per version. Version names are discovered at build time; contents are fetched and rendered at runtime. `public/WIP.md` is rendered the same way as the unreleased entry and doubles as the author's roadmap. Visiting the change-log page sets the stored last-seen version to the latest, which drives a "new" marker in the footer, shown for any other version, patch bumps included (`version_equal` is plain equality). `load_change_log` (`Utils/Changelog.ts`) caches each rendered version for the session and returns null on a failed fetch, which the page shows as an error; `computedAsync` drops a fetch that lands after the version changed.
