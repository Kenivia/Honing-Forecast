# UI components

Shared pieces under `frontend/Components/Common/`, plus the tooltip content built on them.

## HoverTip

Every hover tooltip on the site, including the material and gold graphs' (Chart.js's income graph draws its own on the canvas). The look is the `.tooltip-card` class in `shared.css`, taken from the original material-graph tooltip: a `--bg-bright` card with a 1px `--text-very-muted` border, a small shadow, 6px corners, and 14px text. There is no arrow and no animation.

- Usage: wrap the hovered thing in the default slot (a question mark, a number, a button, a whole instruction column). The content is `text`, or the `#tip` slot for anything else (markup, inline icons, links, buttons). `text` keeps `\n` as line breaks (`whitespace-pre-line`); a template's own line breaks are dropped by Vue, so in a slot a space next to an element has to be written inside it (`full&nbsp;`).
- `sticky` (default on): the card stays open while the cursor is on it (50ms grace to cross the gap), so it can hold links and buttons. Off, it has `pointer-events: none` and closes as soon as the cursor leaves. Purely informational cards (numbers, instruction columns, the graphs) pass `:sticky="false"`.
- Touch: there is no hover, so a tap on the wrapper opens the card, and a tap anywhere outside it and the card closes it (a document `pointerdown` listener while open). A tap on a graph shows the tapped point; dragging scrolls the page instead.
- `placement` (default `bottom`) is the preferred side. The card is centred on that side, 8px away. If it does not fit, `flip` tries the sides in `FALLBACKS`, in order; if none fit, it takes the one that overflows least. `shift` then keeps the card on screen.
- `anchor`: a function returning a viewport point. When set, the card is placed against that point (a floating-ui virtual element) instead of the wrapper. `MaterialGraph` passes its hovered dot, with `placement="left"` and not sticky, so the card follows the dot in both x and y. Pass a new function whenever the point changes, so the position is recomputed.
- Opens after 50ms. `maxWidth` caps the card (default 300px). Emits `closed` when the card closes.
- Width: lines are balanced (`text-balance`). After every update, the content is measured with `Range.getClientRects()` and set to its widest line, because CSS keeps a box with wrapped text at its max width, leaving a gap on the right. Measuring after every update also re-fits the graph's card as its text changes. Line breaks do not change. Block elements inside `#tip` report full-width rects, so such cards stay at the max width. jsdom has no `Range.getClientRects`, so `tests/unit/setup.ts` stubs it.
- The wrapper is an inline `<span>` and is what gets measured. In a flex layout, give it a class so it sizes like the element it wraps (`TierConvertButton` passes `flex flex-col` so the button still stretches (its `compact` prop is the small one-line size used in the calc page's Normal Honing header); the graph passes `block`).
- Tests: the card renders on `<body>` (find it by `[data-side]`), and only while open, so slot content (and anything it reads) is not evaluated until then. Open it by triggering `mouseenter` on the wrapper `span` and advancing fake timers past 50ms (see `open_tip` in `material_graph.test.ts`). Click a wrapped button through `.find("button")`, since the component root is the wrapper.

## Built on it

- `QuestionMark`: a `HoverTip` with class `question-mark`, placed right by default. `text`, or its default slot for formatted content (the upgrade order one holds a "Learn more here" link to `/info/overview`, the Overview page, `Docs.vue`).
- `MaterialCell`: `tip` (HTML) puts a card on a result and underlines it, dotted. The cost distribution's chance column uses it: "X% chance to use ≤ owned" in the graph's wording, the owned total being the chance band's graph line (`owned_lines`) in the band's colour; tradable gold has two, raw cost and overall cost (overall is "…" until the optimizer's gold distribution arrives). An untraded band has no line and no card. A cell's "+N" lines share one non-sticky card saying they are not in the input box.
- Instructions: each juice / book column (`ActualInstructions.vue`) has a card. Normal honing: what to use over which taps, the amount per tap and the total (`juice_info.all_juices[id][piece]`, a `Map` keyed by upgrade index, since Rust's `HashMap` arrives as one), and to buy them if out; "full" only when a breath is used; the pity column has none. Advanced honing: what to use on the first n (or all) grace procs or any n ordinary taps. Inline icons with "A, B and C" joining are `ItemList.vue`. The upgrade's name and icon (`InstructionRow.vue`) open `UpgradeTip.vue`: base chance (normal honing) and each material per attempt, then each optional juice or book with its amount and effect (normal: "+X% chance"; advanced: its two `adv_chances` percentages), and last the special leaps per attempt (`special_cost`, normal honing only, "free tap"). A full-width line under both lists the express event's effects: extra chance (`tap.event`) and artisan rate (`tap.artisan_percent`, normal honing only; advanced honing's `tap` is all 0), and a note when any material has a cost multiplier, shown as "×0.8" beside it (`cost_multipliers`, set in Rust's `parser` from `get_multiplier`, the table `get_data` already applied to `costs`). With none it says "No events affecting this upgrade". The payload forces `express_event` off for now, so that is what it always says.
- The instruction rows are a `TransitionGroup`, so they slide (0.3s) to their new place when the optimizer reorders them. The rows are real subgrid boxes, which the move animation needs.
- The instruction cards are 1032px wide, like the material dist card; the juice column is `1fr`, so it takes up the spare width. Free-tap rows still show the juice instructions, after an annotation block (">>>>>", "Only if all", "free taps failed", ">>>>>") that indents them; its underlined "OK" sets `hide_free_tap_hint` (global, saved) and hides the block on every row. The free-tap controls (`NormalDetails`) stay in the progress column only.

## Icon rarity backgrounds

Every material and chest icon sits on its game rarity background (`public/Icons/Backgrounds/*.webp`, copied from `scanner_setup/templates/Backgrounds`): `rarity_bg(rarity)` in `Helpers.ts` returns the style, and the `<img>` takes the `piece-icon` class (centred, cover); the art is transparent, so the background shows through. Materials: `get_icon_bg(label)`, the rarity from the scanner's `items.json` by label, plus the Enhanced 19-20 books (relic); Gold, Silver and Shards have none. Gear: `get_piece_bg`. Chests: a stack's `icons` entries are `icon@rarity` (set in `Manifest.ts`'s `content_of`, since one icon and title can have several rarities); `ChestIcon` splits them, and older saved entries without `@` show no background. A new material icon `<img>` needs `:style="get_icon_bg(label)"` and `piece-icon`.

## Banners

`Banner.vue` is the one strip across the top of a page's main area: `tone` `warning` (default, red text, `role="alert"`) or `info` (`role="status"`), text in the default slot, buttons in `#actions`. Every use is in `TopBanners.vue` (domain move, unreadable save, other tab open), which `Sidebar.vue` renders first in `.main-stage`; keep them there, since a banner's reactive source read in `Sidebar`'s own render re-renders the whole page (BroadcastChannel updates did, and in Vitest that surfaced as `process is not defined` from RouterLinks after teardown). `download_json` (`Utils/Helpers.ts`) saves their downloads and the backup.

## Calculator layout

- The chest card and the optimizer panel share a row in `Calc.vue` while the chest card is thin; once it is wide (editing, or "Show all chests", 1032px) the optimizer goes under it. The optimizer panel is a fixed 665px, just enough for the simple strategy grid (662px at max-content); widen it if those columns grow.

## Roster setup layout

`RosterView.vue`: rosters are stacked cards; each card's characters sit in `.char-grid`, a CSS grid of `COL_W` (362px) columns (`repeat(auto-fill, min(var(--col-w), 100%))`, centred, so one column shrinks on a phone), at most 3 and fewer as the card narrows. `--col-w` and `--gap` are bound from `COL_W`/`GAP` in the script, the one source. The last cell is a dashed box with "Fetch other characters in the roster", "Add new character" and the sign-in hint, where the next character would go. The card's width is `min(100%, card_width(n))`, counting that cell, so a roster with one character is two columns wide; the +24 in `card_width` is the card padding plus a few px, since auto-fill needs the full 3 columns + gaps to fit.

- Header: the roster name (`NameInput` with `.roster-name`: underline only, like the artisan input, `text-xl`) with up/down move buttons beside it (disabled at the ends, shown with more than one roster), then the linked note and the region.
- Each character is a bordered `--bg-main` box (`.char-row`, an `@container`, `scroll-x`). The box itself is not clickable; its link button opens the character page. Inside, a 2-column grid: a 200px left column (name area on top, ilevels below) and an `auto` right column (class emblem above the buttons). `COL_W` = 200 + 8 gap + 140 (4 icon buttons) + 14 padding and border; if those change, change `COL_W` and the `@min-[348px]` breakpoint together. The 200px fits an ordinary 16-18 character name at `text-xl` (Nunito is proportional: 18 "W"s are 444px; such names scroll in the box).
- Name area: `Uwuowo` with `card` set. The "Char name:" label shows only while the box is empty (its live `draft`, so it goes as soon as anything is typed); then the name is `text-xl`, the same as a linked (locked) one. Its placeholder is the default label, as everywhere; an unnamed character's fetch button says "Enter a name to fetch", and "Fetch other characters in the roster" with no names "Name a character to fetch the roster". The second row (fetch button, or FetchCharButton's small "Last fetched" line and its refresh button when linked) has `pl-1`, so it lines up with the name and the ilevels. `min-h-17` keeps synced and unsynced cards the same height.
- Right column: the class emblem (`ClassIcon` with `large`: the parent sizes it, `aspect-square h-full max-h-22`, 30% opacity) fills what the buttons leave, so it is 88px over one row of buttons and shrinks above the 2x2 grid. An unknown class is a button around it that opens a class picker popup (`CLASS_KEYS` capitalised, the lostark.bible names; a focused "Search:" box filters them by substring, Enter picks the first match); the pick is written to `class_name`, which any fetch or sync overwrites.
- Buttons: a `RouterLink` styled `.icon-button` to the character page (`arrow-up-right-from-square-solid-full.svg`, its viewBox cropped to the glyph), then `IconButton`s: drag handle, duplicate (a `HoverTip` with class `flex` saying "Duplicate this character", then "<label> has been made" until the tip closes, via `HoverTip`'s `closed` event) and delete (only with more than one character in total). One row from 348px of card content width, else a `w-fit` 2x2 grid of `auto` columns centred under the emblem (`grid-cols-2` is `minmax(0, 1fr)`, so the column collapsed and the buttons overlapped). Under 276px the card scrolls sideways rather than overlapping anything. Delete asks in a `Popup` only when `has_edited_mats` (`RosterConfig.ts`): bound/special budgets, chests or forbidden chests differ from a new profile, or, for a roster's last character, the roster's mats or chests are not empty. Grid, tier, name and class (what a fetch sets) are ignored.
- Characters reorder by drag and drop within their roster, from the handle only: `vue-draggable-plus` (`VueDraggable`, SortableJS, `handle=".drag-handle"`, `draggable=".char-row"` so the add cell stays put) around the grid, `:model-value` the roster's list and `update:model-value` calling the store's `reorder_roster(roster_id, ids)`, which puts the roster's profiles in that order in the slots they already take. The placeholder is the faded `.drag-ghost`. Playwright's mouse drags work in Chromium (native HTML5 drag), but not through an open popup overlay.

## Icons and scrolling

- `.icon-button` (`shared.css`) is the one small square icon button style (2rem, 4px padding). `IconButton.vue` renders it with `icon` (a file under `public/Icons/`) drawn in the text colour, or its slot instead (RefreshButton's spinner, the chest panel's ✓): the chest panel's buttons (a `w-8` spacer stands in for a missing one), the roster card's (its link is a `RouterLink` with the same class and mask), and `RefreshButton` everywhere it shows. The roster header's arrow buttons are plain `.icon-button`s drawn by CSS.
- `icon_mask(path)` (`Helpers.ts`) is the style for any icon drawn as a `bg-current` mask (`IconButton`, `ClassIcon`).
- `ClassIcon`: `size-5` by default; `large` leaves the size to the parent and scales the unknown class's "?" with it (`@container-size`, `55cqh`) and drops its "Class not imported" title.
- `scroll-x` (`@utility` in `index.css`) is "scroll sideways, clip vertically": the header tabs, the Characters tabs, the main stage, the instruction streaks and the roster card. `scrollbar-width: thin` is already on every element (`index.css` `*`). `.outer-grid` in `shared.css` writes the same rules itself, since `shared.css` is not processed by Tailwind.

## Info pages

Guide.vue is four steps (character, materials, instructions, progress); its images come from `pnpm guide-shots` (`Browser harness/Overview.md`). Guide.vue and Docs.vue share prose styles (heading/paragraph indent, list markers, plain `th`/`td` tables) from `frontend/info.css`, scoped under the `.info-html` class on each page root. The Discord/GitHub contact line is `ContactFooter.vue`, rendered by `InfoView.vue` under every Info page.

The Overview page (`Docs.vue`) holds `Info/Demo/OptimizerDemo.vue`: two fixed Serca vambrace normal honing upgrades (+11 and +10, text only), a juice & book strategy radio (Optimal / Optimal x10 / No juice / Full juice, one choice for both upgrades, the calc page's `NormalOverride`s; Optimal x10 is the Optimizer override on a copy of the profile at streak length 10, and switching to or from it reruns the optimizer; plus Custom: a panel above the sliders of small juice icon toggle buttons (ticked / crossed out with the instructions' `can-disable-icon-wrapper`), one row per upgrade and juice id, one box per tap before the custom plan's current pity, so rows shrink as early taps are juiced; selecting it copies the shown strategy's juiced taps before its pity, and it is sent as the plan's `state` with the Optimizer override), and owned bound sliders for fusion and each juice the two take (Glacier's and Lava's Breath; a juice's max is every tap but the pity of both upgrades juiced, at full-juice pity, `demo_juices`). The plan is the real wasm's: `demo.ts` builds a fresh tier 1 profile at streak length 1 and a `payload_for` with nothing owned but the fusion and juice (bound), fusion and the juices at the demo's own `PRICES` (an NA snapshot, fusion inflated to 800 so the optimizer juices some taps with nothing owned; T4 Fusion gets the same price, or converting would undercut it), and every other material disabled (endless and free). The demo has its own two worker bundles: any slider reruns the optimizer, and each of its results (and a strategy change) reruns the histogram on `states_payload` with the strategy as the override and `dist_plan` 0. Each upgrade shows its plan with `ActualInstructions.vue`, which takes optional `juice_info`, `tier` and `working` props in place of the calculator's stores. The heatmaps read the histogram's `normal_dist`: joint tap probability (log colour from the least to the most likely cell) and the fusion each outcome has to buy (linear, white at 0 to orange at both-pity with nothing owned). The axes, the orange scale and the slider stay at the no-juice pity (`max_taps`, a copy of Rust's `probability_distribution` integers; keep it in step), so juice only empties the cells past the new pity. Below, the histogram's `gold_dist` goes through `MaterialGraph`, always non-cumulative, with the average `-metric_per_plan[0]`. `Heatmap.vue` wraps `chartjs-chart-matrix`, whose y axis is reversed by default (set `reverse: false`). Its `square` plugin sets the box height after each layout so the plot area is nx:ny and every cell is square.

The Overview's leftover-value section holds `Info/Demo/LeftoverDemo.vue`, purely illustrative (no data, no wasm): three band dropdowns stacked below the chart, in the right half of a two-column row whose left half is the default slot (Docs passes a line of text) (the `LeftoverBands` select grid on a local `BandPlan`, default `MAIN_BANDS`, not the store), a noUiSlider with 3 handles splitting 0–100 into bound / roster / tradable owned / bought (segments coloured `--bound`, `--roster`, `--tradable`, `--gold`), and a Chart.js line of net cost against material used on fixed axes (x 0–100, y −8–100 so flat segments clear the bottom edge): each band's slope is its value (nothing 0, taxed sell 0.95, market 1), buying is 1, and the curve starts at (0, 0), so net cost 0 is a dotted "Actually spending gold" line at the owned bands' total value (the curve always meets it where buying starts). Its `backdrop` plugin paints the plot white and draws that line.

## Market page

`/market-mats` has child routes like the character page: `materials` (`BudgetGrid.vue`, the default) and `gems` (`GemsView.vue`), picked by side-bar links; the region selector is shared; the material fetch controls and the roster selector show on Materials only (Gems uses the region of the roster last picked there). Gems: lowest buy-now per kind (Doomfire, Blazing) and level (10 to 5) from the latest pass, each also as gold per Lv. N (a Lv. M gem is 3^(N-M) of a Lv. N, since three fuse into the next; N picked 1 to 10, not saved), and a "Highest value" card with the cheapest per Lv. N of each kind.
