# Income

The character's Income sub-page (`/:char/income`, linked under Scanner in the sidebar): the roster's budget snapshots (`Manifest.md`, "Snapshots") as one character has them over time, a graph of the optimizer's two metrics over them and the weeks ahead, and an estimate of income per week. It is also the snapshot explorer; there is no other snapshot page.

Code: `Components/Character/Income/` (`Income.vue` the page, `IncomeGraph.vue` the Chart.js graph, `IncomeJobs.ts` the optimizer runs), the pure parts in `Utils/Income.ts` (the fit, `owned_at`, `chain_of` / `next_in_chain`, `projected`, `range_of`, `steps_of`, `has_band`), and `snapshot_payload` / `states_payload` in `PayloadBuilder.ts`. `tests/income.test.ts` covers the resets, the fit, a Serca snapshot's values and a reload; `tests/unit/income-choices/` the edge cases, the job queue and the page; `income-fixture.test.ts` there runs the page over `tests/income-fixture.json`, the whole chain included.

**The fixture** (`tests/income-fixture.json`, also a Backup → Import file for trying the page by hand) is the real save (`tests/honing-forecast-2026-10-17.json`) with five weeks of made-up snapshots for roster 0 (Toneema active, from 2026-09-18 to 2026-10-20): materials rising linearly at fixed rates, a Before / After export pair a week, a Manual one, a spend with a break at the fourth export (a chest stack drops too), and an ignored 5x Gold outlier after the last. It has no optimizer results (they hang on the payload hash, so the page runs them; tests store fake ones). `node "scripts/mock income/run.mjs"` rebuilds it (`make.ts` holds the rates); each rebuild gives the profiles new ids.

## What a snapshot holds for a character

`owned_at`: per label of the character's **current** tier, its bound band and the roster's two bands, with `merge_lower_tier` (T4 into Serca, tradable T4 into roster bound), plus what the chests give (`chest_gains` of `process_chests` over its own and the roster's chests). Free taps are the special leap row, all char bound (`[free taps, 0, 0]`): the free-tap budget (T4 special leaps merged) plus every band of the special leap gains. Otherwise they go through the same code as any material; their roster-bound and tradable values and income are always 0.

**The chests are opened as an optimizer run decides.** A snapshot keeps no chest states. Each snapshot is run through the optimizer, then the histogram with the optimizer's states, under the character's current upgrades and settings and the snapshot's own materials, chests and prices (`snapshot_payload`, the calculator's own `payload_for`; prices are the region's per bundle key and its bundle choice, stored in the snapshot). The result, the chest gains and the two metrics the calculator shows (average tradable gold spent, value of the leftovers, as `metric_per_plan`), is kept in the snapshot under the character, by a hash of the payload (`results`, the latest four per character; storing a hash already there replaces it, since one run is stored into every job of its hash). A run of a character the snapshot did not have gives it an empty entry (name, no budgets) to hold the result. Upgrades changing means new hashes and new runs. Until its run is back a snapshot's values use every chest on its first option, as Rust does without a state. "Now" is run the same way and kept for the session only.

`IncomeJobs.ts` builds the runs (`job_for`); they run through `WasmInterface/OptimizerJobs.ts`, shared with the Choices page, each an optimizer run then a histogram of its state, handed to the job's `store` with that state. **The runs are one chain** (`chain_of`, `next_in_chain`): every snapshot oldest first (ignored ones only while selected), then now, then the weeks ahead; Income queues only the first not done, so one runs at a time and the second worker idles. Each starts from the latest optimizer state of the session before it (`warm`, `states_payload`), or cold. States are kept for the session only (`state_of`), so after a reload the first run not stored starts cold. The hash is of the payload without that state, so a stored result is found again whatever ran before it, and a change earlier in the chain does not re-run what is stored. A Before export snapshot has the same payload as the export before it and is run again all the same (one run serves several jobs only within one `queue_jobs`). Leaving the page cancels them. The histogram's payload is built with the optimizer result's `prep_output.juice_info`, so it does not need the calculator's histogram to have run.

## The estimate

- Uses "After export" and "Manual" snapshots that are not ignored, plus now while it differs from the latest snapshot (materials and chests compared, prices not); a now equal to it would add a flat point. There is no checkbox for it.
- One least squares slope per material through runs of points, each run with its own intercept (`fit`, which returns the slope only). A run starts at a snapshot the user marked "Start a new line here" (`breaks`, for a spend before it); there is no automatic break at decreases, since a different chest state or a chest opened another way would look like one. Ignoring (`ignored`) drops a point altogether. Both are saved on the snapshot, for every character, and both apply to every material. The steps and days above the table are summed within runs.
- Week boundaries (Thursday 10:00 UTC, both regions) are only drawn.

## The page

- **Band**: Char bound, Roster bound, Tradable; the table shows that one band alone, both its "Owned now" and "Income / week".
- **Cells that do not exist in game are not in the table** (`has_band`): Silver only under Roster bound, Free taps only under Char bound. A few roster-bound chests do hold special leaps ("Special Honing: Circulated Leapstone Chest" 61001469, "Special Honing Material Selection Chest" 61106501, "Chest for the Fated Moment" 70705100, "Clear: Flame of Darkness, Tarkal" 71650029, among others), but they are rare, the leapstones themselves are char bound, and `owned_at` counts every free tap as char bound. A hidden cell's manual rate counts as 0.
- **The graph** (`IncomeGraph`, the only one): the two metrics (average tradable gold spent, value of the leftovers) of the estimate's points that have a run back, joined, on one y axis, with a legend; then a dashed "projected" line with points from now through the weeks ahead. Week lines, now and the selected snapshot as vertical lines. There was a graph of the materials themselves too (one at a time, with the fitted lines); it was dropped as redundant.
- **The weeks ahead** (`future`, `projected`): now plus k weeks of the table's income (auto or manual, as the table is), per band and material (free taps char bound), rounded, never below 0, for each whole week to the end of the range; chests and prices as now. Kept for the session, like now; a rate change makes new hashes and runs.
- **The x range** is centred on now, the larger of five weeks and the age of the oldest snapshot either side.
- **Timeline** under the graph, lined up with its plot area (the graph emits it): a marker per snapshot, "Before export" in a lower lane, ignored ones faded. Hover shows one in the dashboard, a click locks it, as on the slot grid. The selected one is a white line on the graph.
- **Dashboard**: time and kind, "Ignore in the estimate" (not for "Before export"), Delete, the two metrics under the current upgrades, and what changed since the snapshot before (`snapshot_diff` for this character, chest stacks included). Comparing two arbitrary snapshots is gone.
- **Table**: every material of the tier and Free taps, less the hidden cells; nothing known is 0. "Type the income by hand" switches to manual, pre-filling with the auto value (rounded) every cell that was never typed; typed values are kept. The auto value stays beside each input. Typed values go through `parse_locale_float`, a leading minus allowed. The rates, manual or auto as the table is, drive the weeks ahead. A break shows as a bar before the snapshot on the timeline.
- **Manual income is saved** per band: char bound and free taps (under the special leap label) in the profile (`bound_income`, `income_manual`), roster bound and tradable per roster (`roster_income[roster_id]`, `[roster bound, tradable]`, made on the first write), so every character of the roster shares them. Nothing reads them outside this page yet.
