# Income

The character's Income sub-page (`/:char/income`, between Calc and Choices in the sidebar; dev builds only until released, in `Router/index.ts` and `CharView.vue`): the roster's budget snapshots (`Manifest.md`, "Snapshots") as one character has them over time, an estimate of income per week, and a graph from now on of what the selected upgrades cost against what will pay for them. It is also the snapshot explorer; there is no other snapshot page.

Code: `Components/Character/Income/` (`Income.vue` the page, `IncomeGraph.vue` the Chart.js graph, `IncomeJobs.ts` the optimizer runs, `IncomeSources.vue` the Auto income's settings), the Auto income in `Utils/IncomeSources.ts` ("Auto income" below), the pure parts in `Utils/Income.ts` (the fit, `owned_at`, `chain_of` / `next_in_chain`, `projected`, `range_of`, `steps_of`, `has_band`), and `snapshot_payload` / `states_payload` in `PayloadBuilder.ts`. `tests/income.test.ts` covers the resets, the fit, a Serca snapshot's values and a reload; `tests/unit/income-choices/` the edge cases, the job queue and the page; `income-fixture.test.ts` there runs the page over `tests/income-fixture.json`, the whole chain included.

**The fixture** (`tests/income-fixture.json`, also a Backup → Import file for trying the page by hand) is the real save (`tests/honing-forecast-2026-10-17.json`) with five weeks of made-up snapshots for roster 0 (Toneema active, from 2026-09-18 to 2026-10-20): materials rising linearly at fixed rates, a Before / After export pair a week, a Manual one, a spend with a break at the fourth export (a chest stack drops too), and an ignored 5x Gold outlier after the last. It has no optimizer results (they hang on the payload hash, so the page runs them; tests store fake ones). `node "scripts/mock income/run.mjs"` rebuilds it (`make.ts` holds the rates); each rebuild gives the profiles new ids.

## What a snapshot holds for a character

`owned_at`: per label of the character's **current** tier, its bound band and the roster's two bands, with `merge_lower_tier` (T4 into Serca, tradable T4 into roster bound), plus what the chests give (`chest_gains` of `process_chests` over its own and the roster's chests). Free taps are the special leap row, all char bound (`[free taps, 0, 0]`): the free-tap budget (T4 special leaps merged) plus every band of the special leap gains. Otherwise they go through the same code as any material; their roster-bound and tradable values and income are always 0.

**The chests are opened as an optimizer run decides.** A snapshot keeps no chest states. Each snapshot is run through the optimizer, then the histogram with the optimizer's states, under the character's current upgrades and settings and the snapshot's own materials, chests and prices (`snapshot_payload`, the calculator's own `payload_for`; prices are the region's per bundle key and its bundle choice, stored in the snapshot). The result, the chest gains and the two metrics the calculator shows (average tradable gold spent, value of the leftovers, as `metric_per_plan`), is kept in the snapshot under the character, by a hash of the payload (`results`, the latest four per character; storing a hash already there replaces it, since one run is stored into every job of its hash). A run of a character the snapshot did not have gives it an empty entry (name, no budgets) to hold the result. Upgrades changing means new hashes and new runs. Until its run is back a snapshot's values use every chest on its first option, as Rust does without a state. "Now" and the weeks ahead are run the same way; their results are kept in the profile (`income_results`, by payload hash, the latest `MAX_WEEKS` + 1), so leaving the page or reloading finds them again. Theirs also keep the histogram's `chance_within`, for the chance graph; a snapshot's do not, to keep the save small.

**Now is pinned in time** (`income_now`, saved in the profile): the hash of now's budgets (`budgets_of`: materials and chests, prices not) and the time they were first seen. Now's point in the estimate is at that time, not the clock's, while the budgets stay the same; once they change, the new budgets are pinned at the moment they are first seen. The clock would move now's point, so every rate and every week's hash, and the weeks would re-run constantly. A change of prices still re-runs now and the weeks, as it should. The graph draws now and the weeks from the clock's time, a week apart.

`IncomeJobs.ts` builds the runs (`job_for`); they run through `WasmInterface/OptimizerJobs.ts`, shared with the Choices page, each an optimizer run then a histogram of its state, handed to the job's `store` with that state. **The runs are one chain** (`chain_of`, `next_in_chain`): every snapshot oldest first (ignored ones only while selected), then now, then the weeks ahead; Income queues only the first not done, so one runs at a time and the second worker idles. Each starts from the latest optimizer state of the session before it (`warm`, `states_payload`), or cold. States are kept for the session only (`state_of`), so after a reload the first run not stored starts cold. The hash is of the payload without that state, so a stored result is found again whatever ran before it, and a change earlier in the chain does not re-run what is stored. A Before export snapshot has the same payload as the export before it and is run again all the same (one run serves several jobs only within one `queue_jobs`). Leaving the page cancels them. The histogram's payload is built with the optimizer result's `prep_output.juice_info`, so it does not need the calculator's histogram to have run.

## The estimate

- Uses "After export" and "Manual" snapshots that are not ignored, plus now while it differs from the latest snapshot (materials and chests compared, prices not); a now equal to it would add a flat point. There is no checkbox for it.
- One least squares slope per material through runs of points, each run with its own intercept (`fit`, which returns the slope only). A run starts at a snapshot the user marked "Start a new line here" (`breaks`, for a spend before it); there is no automatic break at decreases, since a different chest state or a chest opened another way would look like one. Ignoring (`ignored`) drops a point altogether. Both are saved on the snapshot, for every character, and both apply to every material. The steps and days above the table are summed within runs. A negative slope (a spend without a break) is shown and used as 0: income is never negative.
- Week boundaries (Thursday 10:00 UTC, both regions) are only drawn.
- The snapshots' runs feed the estimate (how their chests are opened) and the dashboard; none is drawn on the graph.

## The page

- **Band**: Char bound, Roster bound, Tradable, buttons on the table, which shows that one band alone, both its "Owned now" and "Income / week". Session only.
- **Cells that do not exist in game are not in the table** (`has_band`): Silver only under Roster bound, Free taps only under Char bound. A few roster-bound chests do hold special leaps, but they are rare, the leapstones themselves are char bound, and `owned_at` counts every free tap as char bound. A hidden cell's manual rate counts as 0.
- **The metrics graph** (`IncomeGraph`) starts at now: now and the weeks ahead that have a run back, on one y axis with a legend. The metrics are drawn as the calculator shows them (Rust's are negative, `metric_to_text` flips them): average tradable gold spent (gold, solid, falling as income comes), value of the leftovers (light grey, solid), and leftovers plus tradable gold owned (gold, dashed; the tradable Gold band of `owned_at`, which the payload sends as 0, so the cost does not count it). Where the dashed line meets the cost is about when the upgrades can be afforded (`crosses`). A now line and week lines.
- **The chance graph** under it, a second `IncomeGraph` (`percent`: y 0 to 100%) on the same x range with its own x axis; both have a fixed y axis width so they line up. One line per material: the histogram's `chance_within` (chance to succeed all upgrades within the bands summed up to the chosen one, its own buttons "Char bound", "+ Roster bound", "+ Tradable"), for now and each week with a run back that kept it. Only base materials enabled on the calculator are offered (no juices, books or scrolls, no free taps), all on until toggled off in the icon row. Tradable gold is sent as 0, so Gold's "+ Tradable" leaves it out, as the cost does. Band and toggles are session only.
- **The weeks ahead** (`future`, `projected`): now plus k weeks of the table's income (in its mode), plus in Auto what the dated grants give by then (`granted`), per band and material (free taps char bound), rounded, never below 0; chests and prices as now. Kept like now; a rate change makes new hashes and runs. How many: **Weeks ahead** above the graph, typed between `MIN_WEEKS` and `MAX_WEEKS` (session only, not saved), runs exactly that many. Empty is the default (its placeholder shows how many): one more at a time while the last is done and nothing (now included) has crossed, then on to `EXTRA_WEEKS` past the crossing, `MIN_WEEKS` at least and `MAX_WEEKS` at most.
- **The x range** (`range_of`) is now to now plus the weeks projected (`MIN_WEEKS` at least).
- **Take snapshot** is disabled, with a note beside it, while a snapshot would equal the roster's latest (`same_as_latest`, the same check `take_snapshot` dedups by).
- **No upgrades selected**: both graphs give way to a message saying so.
- **Snapshot list** under the graph (oldest first, scrolling): time and kind (coloured by kind), ignored ones faded, a bar above a break. Hover shows one in the dashboard, a click locks it, as on the slot grid.
- **Dashboard**: time and kind, "Ignore in the estimate" (not for "Before export"), Delete, the two metrics under the current upgrades, and what changed since the snapshot before (`snapshot_diff` for this character, chest stacks included).
- **Table**: every material of the tier and Free taps, less the hidden cells; nothing known is 0. Three modes (buttons): **Measured** (the snapshot fit, "-" without enough snapshots), **Auto** (the configured sources) and **Manual** (typed), saved as `income_manual` and `income_auto`. Switching to Manual pre-fills with the mode before (rounded) every cell that was never typed; typed values are kept. The measured and auto values stay beside each input. Typed values go through `parse_locale_float` and are never below 0; the box shows what was kept. The rates in the table's mode drive the weeks ahead.
- **Manual income is saved** per band: char bound and free taps (under the special leap label) in the profile (`bound_income`, `income_manual`), roster bound and tradable per roster (`roster_income[roster_id]`, `[roster bound, tradable]`, made on the first write), so every character of the roster shares them. Nothing reads them outside this page yet.

## Auto income

What the content a character does gives, per week by band, from `frontend/Data/income.json` (the client, `scripts/game_files/income.py`, `Game files.md`) and `frontend/Data/income_community.json` (hand-kept from `Forecasting/Community.md`). Semi-functional: the UI to see how it is used, numbers to be checked. The settings are saved per character in `income_sources` (only what was edited; `config_of` fills the defaults, at the character's achieved item level). `auto_income` gives each source's weekly bags and dated grants, in the tier's labels (`to_tier`: a Serca character's T4 at the ratio, a T4 character's Serca dropped, as `process_chests` does), and sums them into the table's rates.

- **Bands**: materials char bound, silver roster bound, raid gold in the band the client gives it; the playtime reward roster bound.
- **Raids**: up to three, by default the three newest the item level enters on their highest difficulty but Solo. Gold only when "Gold-earning character". A gate's bonus chest, when ticked, adds its materials and pays its gold from the gate's char-bound, then roster-bound, then tradable gold (tradable may go negative). The worth beside it is the Choices page's, read from `choice_results` when that page has run it, else a link there.
- **Kurzan Front / Chaos Rift, guardians**: Tylobic's per-run numbers at the highest item level reached, times runs a week; rested runs count twice.
- **Cube, Hourglass**: per ticket and a clear a week; the hourglass times (1 + sands), sands from the rift runs at 0.2 each, at most 5.
- **Crucible**: every stage of the season the character has not cleared (the first N, typed), each once: those open now granted now, the rest on their unlock date, none after the season ends.
- **Playtime** (days a week), **weekly mission** (claims a week), **guild shop** (the breath chest and the destruction and guardian stones of the character's tier, at the weekly limits; bloodstones are free).
- **Clear Medal shop**: its rows of the tier's own materials, in order, each up to its weekly limit while the raids' medals last; a row can be turned off.
- **Event shop**: the live ones, tokens at 100 per chaos and guardian run, spent as the medal shop, granted weekly until the shop closes.
- **Picks**: an item with options (selection chests, the weekly mission's four) is one select, by default the option with most of the tier's own labels; items that differ only by level share their pick (`pick_key`).
- **Not counted**: Paradise Hell (work in progress), the login track, gems.
