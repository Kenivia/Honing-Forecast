# Scanner pipeline

The scanner reads the player's material counts from a shared game screen, so they do not have to type them in. It is in active development on the `Inventory-scanner` branch. `public/WIP.md` has the author's current task list.

Code: `crates/scanner` (image processing), `frontend/Components/Character/InventoryScanner` (capture and the slot grid), plus scanner operations in the shared wasm worker. What the page shows is in `Slot grid.md`.

Measurements, timings, earlier designs and what was tried and dropped are in `Pipeline tried.md`. Read it only when trying something new here.

## Stages

1. **Capture** (TypeScript, main thread). A video track is read as a stream of frames at 30 a second, and every frame is scanned. The track comes from the browser's screen-share API, or from an uploaded image or video file drawn onto a canvas (a fake stream: an image repeats, a video is drawn frame by frame as it plays and then holds its last frame). Both go through the same frame reader, which keeps up to 8 frames while a scan runs long.
2. **Frame transfer**. For each operation the main thread reads one frame and transfers it to the worker along with the operation. The worker copies its pixels directly into a buffer inside wasm memory, closes the frame, then calls Rust. Nothing else goes in but two flags, the OCR texts that have come back and the slots the user edited by hand.
3. **Is it worth a scan** (Rust). A frame that hardly differs from the last scanned one is dropped here, before anything else. See "Skipping still frames" below.
4. **Locate the windows** (Rust). Each anchor is template-matched inside its bound, and a hit gives a root, the origin of any inventory window it locates, and a brightness estimate. On later frames anchors are re-checked at their known position. See "Anchors and layouts" below.
5. **Detect the page** (Rust). Page-tab templates at fixed offsets from each window origin say which page of that inventory is showing: the one tab that is lit. See "Page tabs" below.
6. **Read slots** (Rust), on every third scan. Each slot of the active page sits at a fixed offset. A slot whose pixels have not changed is skipped; otherwise its crop is compared against every icon template, the closest one that passes wins, and the number strip is sent off to be read. See "Slots" below.
7. **Find the tooltip** (Rust). If an item tooltip is on screen, its text lines are cut out and sent off to be read. When the texts are back, its title, stacked amount and tradability are written onto the slot that was hovered, and a chest's kind and contents go into a separate list of chests. See `Tooltips.md`.
8. **Read the currencies** (Rust). Silver, gold and shards beside their icons in the inventory, the currency window and the bar at the top of the screen, and gold's bands off its tooltip. Apart from the slots; see `Currency.md`.
9. **Result and loop**. Rust returns a small result, not its state (see "State between frames"). On each result the main thread first reads and posts the next frame, then passes the result's text lines to the OCR workers and the rest to the page.

Full-frame search is the expensive step and uses FFT cross-correlation. Everything after the anchor is a cheap fixed-position comparison.

## Anchors and layouts

An anchor is a piece of fixed UI that is template-matched to get a *root*: a position other things are placed from. The ordered anchor list (`ANCHORS` in `anchor_to_slot/anchor_defs.rs`) is the single place that describes them. Each entry has:

- **Variants**: alternative templates for the same anchor, so that one can be covered (cursor, tooltip) while another still holds it. Each has a bound and brightness coefficients. The root comes from the first variant that is found, because variants place it a pixel apart.
- **Bound**: where a variant is searched on every scan. One of: the whole frame (no anchor uses it now, kept for later); a rectangle in UI space; a rectangle in UI space that moves with the storage layout; a rectangle from the top left of the area the game renders into (`Bound::Corner`, for the HUD side: see `Currency.md`); a rectangle in that area whose left and right sides are each measured from its left or its right edge (`Bound::Render`, for the lone inventory).
- **Roam**: only the lone inventory has one: where it can be dragged to, searched as rationed by `search_lone` once it is not at its bound.
- **Inventories**: which inventory windows the anchor locates and each window's origin relative to its root.

A match always *locates*: the root is the matched position minus the template's stored offset, never the bound's own position. So a bound only needs to be roughly right, and its slack does not affect alignment.

The search area is put on whole pixels; cut at a fraction of a pixel it is resampled, which moves an anchor's brightness estimate.

**An anchor template is cut to a whole number of screen pixels.** A template scaled naively comes out `round(w x scale)` pixels wide while the thing it matches is `w x scale` wide, so it is stretched by up to half a pixel, the match settles about half that error off, and every window and its grid sit a fraction out at any UI height 1440 does not divide. So `whole_pixel_crop` takes the largest centred part of the template whose scaled size is whole (`floor(w x scale) / scale` UI units) and the offset moves with the cut, which makes the template pixel for pixel against the screen. It is a no-op at UI heights 720, 1440 and 2160. Slot icons are left alone: there the template and the crop are both `round(61 x scale)` pixels covering the same 61 UI units, so they are stretched alike and nothing is misplaced.

Slot grids and page tabs are defined once per inventory, relative to that inventory's window origin, so the same inventory can be located by several anchors. An inventory's origin comes from the first found anchor, in list order, that locates it.

Current anchors:

- **Storage**: the highlighted Storage button, in a pet-menu and a storage-NPC variant that never show together, each at its own fixed UI-space spot. It locates no inventory. Its position wanders ten times as much as any other anchor's, so nothing is placed from it.
- **One anchor per storage window**, with two variants: the window's sort button at its top left (the char inventory anchor template, identical in all three windows) and something at its top right. For the two storages that is their group of move-to icons. For the inventory it is the search button; the icons next to it are filters and the chosen one lights up. Their roots are the window origins.
- **Char inventory**: the free-floating window, by the same sort button and search button. It is looked for on every scan where the game first puts it, the same way as the currency window, and otherwise over everywhere it can be dragged to. When that search runs is below.
- **Currency**: the currency window, only where the game first puts it and only while the storage layout is closed. It locates no inventory and tells no brightness: the window is see-through. See `Currency.md`.

`AnchorType::in_storage` says which anchors are the storage layout's. Template matching inside an area, with the pass limit, is `find_template`, shared by anchors and currencies.

**Re-checking needs the brightness, and until there is one an anchor is matched again around its place instead** (`check_existing_anchors`). Only anchors without a curve can be found then (the storage icon groups, the currency window), and the currency window alone never gives one.

**The storage layout is a special case, written as one** (`update_anchors`). Roster storage, character storage and character inventory always sit side by side in the same place: one place from the pet menu, and shifted up and slightly left from the storage NPC. So its seven anchors (the button and two per window) are each looked for at their fixed spot, and the layout counts as open while three or more are found. While it is closed, both placements are tried on every scan, which is cheap. While it is open:

- the anchors that are covered are looked for again at their spot on every scan;
- the char inventory anchor is cleared and not searched, since its templates are in every storage window;
- a window whose two anchors are both covered keeps its origin.

So covering the Storage button with the cursor or a tooltip does not drop the layout or start a whole-frame search.

**Where the lone inventory can be.** The game keeps the window inside the area it renders into, not the 16:9 UI block, and native ultrawide behaves as forced 21:9 does. In UI units from that area's top left, its origin ranges from (0, 0) to (right edge − 726, 590 to 595). It first opens at 796 from the right edge and 250.8 down, at either aspect. Both are searched with `WINDOW_ANCHOR_SLACK` around them (`lone_variant`). Measured at 1440p only.

- **The default place is looked for on every scan**, both variants, through `search_anchor` like the currency window. It is cheap, and a window there is never searched for otherwise.
- **Otherwise the rationed search below covers where it can be dragged to** (the variant's `roam`) instead of the whole frame.

**The roam search is rationed** (`search_lone`). While the storage layout is closed and the lone inventory is not found:

- **Both variants are searched when the frame has changed enough**: more than `CHAR_INV_SEARCH_THRESH` (3%) of the thinned frame's samples (the ones `worth_scanning` takes) differ from the frame of the last such search. It is measured against that frame, not the previous one, so a window fading in adds up.
- **Both are searched on the scan the anchor was lost at its re-check.** A match on a dim frame of a fade fails the next re-check, and the frame after may be the last one sent.
- **Otherwise one variant every `CHAR_INV_FORCED_SEARCH_FREQ` (8) scans**, taking turns. These do not move the frame the change is measured against.
- **No rule waits for a later frame**, since a still screen sends none: whatever the last frame is, it was searched unless it is within 3% of one that was.
- **The second variant is only looked for where the first one's root puts it** (the template's place with `WINDOW_ANCHOR_SLACK` around it, timed as `anchors/near`), in the same scan and on every later one. So a variant that gets covered while the other holds is found again when it shows.

**UI space** is 1440p coordinates inside the 16:9 block the game lays its UI out in. The block is assumed to be centred in the capture, which gives the left/right padding of forced 21:9 and the letterbox of a 21:9 game on a 16:9 screen. **Only a full-screen share of a full-screen game is supported.** A windowed game (title bar, uneven margins) puts the game area off-centre: the storage layout and the currency window are then never found, since their bounds have 2 to 8 UI units of slack, and the 21:9 detection looks at the wrong rows.

## Page tabs

- **A tab is lit when its active template passes and beats its inactive one by `PAGE_NUM_LEAD` (0.1)**, and dark the other way round. Anything else says nothing. A lit tab leads by about 0.2, also with the cursor on it.
- **A tab under the cursor lights up a little**, scoring around the tabs' 0.8 limit as active, so the lead is what tells.
- **The page is the one lit tab, else unknown**, and then no slot is read. A tooltip is tied to the slots of the page last lit, for as long as nothing says it changed (`Tooltips.md`). Taking a tab that matched neither state as the active one is wrong: a hover label over a tab hides it.
- **Character storage has a fifth tab, Gear Space** (crossed swords, left of 1), with no template. While it is open no tab is lit, so nothing is read.

## Skipping still frames

- Every frame is thinned to one pixel in eight each way and compared with the last scanned frame. It is scanned when more than 0.5% of those differ by more than 16 in a channel: a tooltip showing up or moving on, a page turning. The cursor moving alone is under that. The whole frame is compared, so a game world animating behind the windows keeps the scanner busy.
- After the last change the next six frames are still scanned, so the slots get their turn.
- A frame is also scanned while something is unfinished: the current hover is waiting for texts (its next read is cut when they are back) or has just gone missing, or slots were left over by the time budget.
- A change too small to count is not picked up until something bigger happens. A slot's number changing on its own is one.
- A skipped frame costs the frame copy and its wasm call. OCR texts that come back are still applied. A still image stops being scanned after about 30 frames.

## OCR runs elsewhere

A scan never waits for OCR. A line of text takes 30 to 100 ms to read in the browser and cannot be interrupted, which is several frames.

- **Everything about reading text is in `crates/scanner/src/ocr`.** `jobs.rs` has the job and the queue, `text.rs` and `number.rs` make a crop into the strip the recogniser takes, `recognize.rs` runs the two engines, which `load_ocr_engine` in `interface/setup.rs` loads.
- **Jobs.** Whatever needs reading (a slot's number, a tooltip's title lines, amount crops and chest rows) is cut out of the frame as captured and queued with an id as a `Line`: the RGBA crop, the brightness estimate of its frame and its kind (`Text`, `Yellow` for a tooltip amount read by its yellow alone, `Number` with the slot's normalised icon crop and the name of the template it matched). The scanner does nothing else to it. A line identical to one seen before (its pixels, its kind and, for a number, its icon crop and template) gets the old id and is not read again, which makes a tooltip standing still on a lossless capture nearly free. The brightness estimate is left out of that comparison on purpose: it wobbles in the last digit from scan to scan. A job also names the read it is a line of (`group`, 0 for a slot's number). A line still waiting that is asked for again with more urgency is sent again, and the page moves the waiting one up.
- **The reader prepares it.** `Line::strip` makes the 64 px grey strip (one byte a pixel, which `ocrs` takes as it is) and `Line::read` recognises it, both in the OCR worker. A slot's number needs its icon's base template for that, so the OCR workers load the config too and a job only names the template.
- **Out and back.** Each scan result lists the new jobs. The main thread (`OcrRelay.ts`) hands them on untouched, one at a time, to OCR workers: more instances of the same worker, which load the model and the config. Their texts go back in with a later scan, where `apply_ocr` gives them to whatever was waiting. The scanner worker itself has no recogniser. Crops and slot images are transferred, not copied, on both hops.
- **Workers.** One per four hardware threads, at most three. Each loads the 10 MB model twice (once for text and once for slot numbers) and the config. A line in a wasm worker is several times slower than natively, where `rten` runs each model call on a thread per physical core.
- **Slot numbers are read with digits only.** A job says whether it is a slot's number (`numbers`), and those are decoded with the alphabet cut to `0123456789.+-`. `ocrs` fixes the alphabet per engine and its model cannot be shared, hence the second engine. It is the same model with other characters masked out when decoding, so a "9" no longer comes back as "g" or "S". Tooltip amounts still use the full alphabet; not tried there.
- **Order** (`pump` in `OcrRelay.ts`). Lowest priority number first; then a read some line of which a worker already took, since a read is of no use until all its lines are back; then the newest read, which is what the user is hovering now; then by id. A job's priority is how many reads of its kind its hover had already sent, plus 100 for a tooltip beside no slot we know that is lit up (`Tooltips.md`, "Which tooltips are read first"). Slot numbers are priority 0.
- **A batch is one line** (`BATCH` in `OcrRelay.ts`; any size works). A worker cannot be interrupted, so a batch is what a new hover's first read may have to wait for; a bigger batch reads a line only a little faster.
- **Nothing is lost when OCR falls behind**, it is only late: the queue is drained in priority order, and the hover it belongs to is kept until its texts arrive.
- **Lifetime.** The OCR workers start and stop with the scanner worker, so ids never cross from one scanner state to the next.
- **Natively** there is no second worker: `run_ocr_inline` reads the queue on the spot after each scan, so every text is back with the next scan, and `native::read_rest` reads what is left at the end of the input.
- **The native bins share one setup** (`native.rs`, not compiled for wasm): `native::new_state(width, height)` loads the config and the recogniser from `public/` once and returns a state with the frame buffer the bin fills, 21:9 and brightness on auto (a bin replaying a capture sets them from its start record).
- **`tooltip_test` repeats exactly**, so its output can be diffed before and after a change. The slot step's time budget is off in the harness (`no_slot_budget`; `SLOT_BUDGET=1` puts it back, and results then move with the machine's load), and nothing goes by hash map order (a tie between votes goes to the smaller value, the brightness average is summed in anchor list order, the shortlist's table is built in name order).

## Slots

- **A shortlist of 16** (`SHORTLIST`). Each icon is kept as the mean colour of 12 cells of its top rows, and only the 16 closest to the slot that way are compared in full. Comparing all of them is some twenty times slower and recognises nothing more.
- **Decoys.** Templates of things we do not count that look like an icon of ours: another chest in a similar trim, the same art on another rarity's background, a T3 fusion material against the T4 one (`Game files.md`, "decoys.py"). They are tagged `Decoy` and named `~<icon>@<rarity>`. A slot is compared with the 16 nearest icons and, shortlisted apart so they cannot crowd an icon out, the 16 nearest decoys. An icon that scores under the closest decoy does not count, so a slot holding a look-alike matches nothing and shows as irrelevant. A decoy's score has no pass limit: it only has to beat the icon. Without them the score cannot tell true matches from look-alikes (`Icon matching bench.md`). A decoy is compared the way the icon was: whole, and with the same overlays left out (below), the better of the two counting, so a look-alike chest with its item level across it still vetoes. Matching a changed slot takes about twice as long with them.
- **Overlays: the item level and the clock.** The game draws two things over an icon. Both go through one table (`OVERLAYS` in `slots/constants.rs`) and one function (`overlaid` in `slots/utils.rs`): an entry is the part of the compared icon it covers (1440p), how much the score has to gain with that part left out for it to be there (`gain`), and which icons can have it. A third overlay is a third entry.
  - **Item level.** A chest that asks for one has a helmet and "1640" written across rows 18 to 33 of the 39 compared, over the full width. Only icons with a chest that counts and has a level can have it (`level` in `chests.json`, the game's `ReUseBalanceLevel`; with the irrelevant rows' levels in too, plain chests of another art pass as such an icon). A slot with it is `levelled`, which says which of the icon's chests it can be.
  - **Clock.** An item that expires has a stopwatch in the bottom left corner: 20 wide, from row 13 down. It is opaque, black in a gold ring. Any icon can have it. The game's tables say which items expire (`Game files.md`), but an expiring item is drawn with the art of the plain one, so the table would not narrow it. It changes nothing but the match: a stack with a clock counts like one without.
  - **The rule.** Each set of the overlays an icon can have is scored with those parts left out. The set that gains the most over the sum of its gains is the one on the slot; none, when no set gains that much. The slot then has to pass the usual limit with that score. Both gains are 0.02: leaving the part out moves a slot without the overlay by under 0.011 and one with it by 0.025 or more. A fixed "fails whole, passes without" rule cannot work, since plain chests near the limit pass without the rows too.
  - **The hover highlight is judged with the same parts left out** (`looks_hovered`). A levelled slot's best score is without the rows, so compared whole it would count as lit on every scan.
  - **An icon more than `OVERLAY_REACH` (0.1) under the limit is not tried with anything left out**: no overlay was seen to hide more than 0.071.
  - **Not seen**: a slot with both, so where the helmet goes under a clock is a guess (both parts are left out together). An icon whose corner is nearly black gains little from the mask, and loses as little whole.
- **A slot is several icons.** Plain chests in other trims, and one chest on two rarities' backgrounds, score within a hundredth of each other. So the best icon is the slot's, and every other that passes within 0.02 of it is kept as an alternative; a chest read off a tooltip counts for the slot when it is drawn with any of them. Taking only the best leaves chests without a slot.
- **Every third scan.** Slots change slowly and a tooltip can be gone in a few frames, so the slot step runs on one scan in three (10 times a second at 30 fps).
- **Unchanged.** A slot whose raw pixels hash the same as last time is skipped outright. Otherwise it is compared with the crop last seen, and only a slot that differs is matched against the icons again, from that same crop (`check_through_all_icons` takes it). On a compressed recording most slots are compared rather than skipped, since compression changes their pixels.
- **Slots that match nothing are remembered too** (empty, unknown, or covered), so they are not matched again on every scan. Their unchanged test is strict (`UNMATCHED_UNCHANGED`, 0.995), or an icon the cursor is slowly leaving would stay unrecognised.
- **A time budget** (`SLOT_BUDGET`, 60 ms a look) stops matching and number clean-up for the scan; the slots left over are done on the next looks. Opening a page therefore takes about a second and a half to read fully, instead of holding up one scan for 0.7 s. The slot step is budget-bound, so making it cheaper buys slots read sooner, not milliseconds.
- **The number** is cleaned up on the spot and its strip sent to OCR. Until the text is back the slot keeps its previous amount if it holds the same icon.
- **The amount is a vote over the slot's last five reads** (`vote_amount`), compared by their digits, the newest winning a tie, forgotten when the icon changes. A wrong read is usually the last one a slot gets before its page goes away (cursor or highlight on it), and a recognised slot is not re-read while its icon area stays within 0.95 of the last crop. The cost of the vote: a number that really changes needs as many new reads as the old one had, and a still screen gives one.

## State between frames

- **Starting costs a few hundred ms**, mostly wasm init and the first scan: the config's pixels are msgpack bin, so they decode as `Uint8Array`, are posted to the scanner and each OCR worker as one copy, and reach Rust in one copy (`serde_bytes` on `OneIconConfigJs`). As arrays of numbers they took seconds (`Pipeline tried.md`, "Startup").
- Everything stays in Rust for the life of the worker's wasm instance: the `ScannerState` (a thread-local in the wasm crate), the base templates and a cache of templates scaled to the current resolution. The reserve operation builds all of it: the wasm crate reads a `ReserveInput` (forced 21:9 and brightness settings, buffer size, config), sets the config (`set_config`) and makes the state with `ScannerState::new`. The state is never serialised or deserialised, so its structs carry no serde; only what crosses the boundary does (addresses, tradability, edits, chests, the buffer info, the config's icons).
- Consequently the scanner worker must not be restarted between frames, unlike the optimizer worker. A new capture, a settings change or a wiped scan (see below) terminates it, so each starts with empty scan state.
- A scan returns a `ScanResult` (`scan_result.rs`): the text and status of every slot looked at so far (matched or not, but not the ones edited by hand), the hover summary, the buffer info and the new OCR jobs, every time; slot images and the chest list only when they were written since the last result. A slot's image is the whole slot with its number, as last recognised, or as last seen while it never was. Images cross as `Uint8Array`. The state marks what was written (`changed_slots`, `chests_changed`) and the wrapper clears the marks after serialising.
- `result()` works out every slot's status anew on each scan; chests' contents are sorted once at load (`Variant::sorted`) so comparing them is cheap.
- The first scan of a loop asks for `full`, which sends everything, because the page may have been remounted or a reply dropped. A reply whose `full` does not match the request is ignored.
- Every scanner result carries the buffer info, which is how the capture card knows a state exists. The worker keeps its own copy of the pointer from the reserve result.
- The page (`ScanStore.ts`) merges every result into plain maps and reuses the image objects, so slots that did not change do not redraw their canvases. The grid itself is updated at most four times a second.

## Who owns the stream

- The capture stream and its frame reader live in one "frame source" object on the main thread, stored in the roster config next to the scanner worker bundle. It is shared by all characters and never persisted. Because it carries the user's screen-share permission, it outlives the capture component: leaving the scanner page only pauses the loop, and coming back resumes it without asking again.
- Each frame is transferred to the worker with its operation, so exactly one side owns it and the worker closes it.
- **Never `console.log` scanner results per frame.** They carry images. Firefox keeps recently logged objects alive even with DevTools closed, which leaks several GB per minute on screen share. Chrome only does this with DevTools or an automation client attached. The worker and worker bundle log only the operation name for scanner operations.
- Stopping capture terminates the worker, which frees the frame buffer and the Rust statics together. The next capture reserves again.
- **The scan belongs to the active character** (`ScanSwitch.ts`, a router guard). Going to another character wipes it (`wipe_scan`: worker terminated, `reset_scan`, the roster cover back to its default) but keeps the stream; the capture component reserves a fresh state when it next runs, at once if it is mounted with a stream or replay running (a replay starts from its beginning). **Reset scan** beside Stop is the same wipe, enabled while capturing or while there is anything to clear. If the scan has anything not exported (`scan_unexported`: there is progress and the manifest's read pages are not as the last export left them), the navigation is held and `ScanSwitchDialog.vue` (in `App.vue`) offers: move the scan to that character, wipe it, or cancel. Moving keeps the worker, the store and the cover as they are and goes to that character's scanner page; the manifest then works out saved pages, the cover and the others for the new character by itself, since nothing in the scan state names one. To another roster the cover goes back to its default too, since it was chosen against the old roster's saved reading, and the dialog says that roster storage and the roster-wide currencies will count for the new roster. Nothing read is lost either way: a covered window is only left out of the manifest, its slots stay in the store.
- A worker reply is delivered to whichever callback was registered last, so the scan loop ignores replies it has already handled or that belong to a stopped loop.

## Where the time goes

Every scan is timed. Rust stages accumulate in `timing.rs` (`timed("name", ...)`) and are drained by the worker after each call; the worker and main thread add their own parts, and one record per scan is pushed to `window.__scan_timings`. `Browser harness/Screen scanner.md` says how to read it. The OCR workers' own stage timings (`ocr/preprocess`) are drained and dropped by the worker, so preprocessing only shows inside a batch's `took`.

The last full breakdown is in `Pipeline tried.md`. In short: at 3440x1440 the frame copy and the result's way back are as large as the scan itself; the slow tail is the slot step, held to its budget; OCR is not short of workers, its long waits are bursts.

## Debug captures

A user records a session, corrects the grid by hand and sends the file in. It is run again on any later build (a re-run): the frames are what was recorded, the reading is this build's. Code: `crates/scanner/src/dev_utils/capture.rs` (format, input recorder, replay), `Capture.ts` (the page's side), the buttons on the capture card in `Stream.vue`.

- **Per frame the scanner was sent, one record**: its pixels. Nothing else the scan took in is kept: not the OCR texts, the time budget or the edits made while recording. Only the end state counts (below).
- **Who writes what**: the page writes the start record (msgpack) and the end record (JSON) at download; a recorder worker of its own writes each input.
- **The recorder worker** gets each frame from the scanner worker, not from the browser: with the scan option `forward` the scanner copies the frame it has just copied into wasm memory (`pixels` on the result, transferred) and the main thread passes it on (`record_input`). Taking it from the browser a second time was the expensive part (`Pipeline tried.md`, "Recording"). The recorder copies it into one of two buffers in turn (`InputRecorder`), so the frame before is still there, and stores the XOR with it, RGBA, through LZ4 (`lz4_flex`), or nothing when the two are the same.
- **Frames waiting at the recorder are capped** (`RECORDER_BACKLOG`, 8). Past it recording stops and the card says the computer could not keep up; what was recorded can still be downloaded. `Download capture` waits for the recorder to finish.
- **One wasm instance per worker**: the worker keeps the promise of its first `init()`. The recorder gets frames back to back, and a second `init()` while the first was loading made a second instance, which lost the frame before.
- **A capture starts from an empty state**, since the state cannot be saved. So `Record debug capture` restarts the scanner, and anything else that restarts it (settings, character, a new capture) throws away what was recorded. `Stop recording` stops forwarding; the scan goes on so the grid can be finished and corrected.
- **The file** (`.hfcap`) is `HFCAP005`, then records of a tag byte, the payload's length as a little-endian u32 and the payload: `S` the start (capture size, forced 21:9 and brightness as the user gave them, which on auto are detected again on replay, and the git commit the page was built from, `git describe --always --dirty` as a Vite define, for information only), then `I` per frame, then `E` the end. All msgpack with field names but the end.
- **Only the hand edits of the end record are right answers.** The rest of it (`slots`, `chests`, the overrides and switches, the `manifest`) is what the page showed at download, wrong readings included: a capture is usually sent in because something was read wrong, and it may not have been corrected at all.
- **Correcting a capture**: `cargo run --release --bin capture_edit -- <file.hfcap> set "Roster 0 5,1" amount=13 tradability=RosterBound [item=<icon>]` adds or replaces a hand edit in the end record (the slot named as the page's edits name it; the item defaults to the icon the page showed there), `remove "<slot>"` drops one, `list` prints them, and `accept` sets every slot to what the page showed (for a capture whose whole reading was checked by hand; it refuses one with a slot still unresolved). An irrelevant slot's edit has no item. Only the end record is rewritten. Before setting a slot, look at its tooltip in the frames (`capture_replay --slot` for the hovers and scans, then `--dump` those scans) rather than trusting any reading. An edit says icon, amount and tradability, not which of two chests drawn alike it is.
- **Checking a build against them**: `capture_replay <file.hfcap> --check` says, per hand edit, whether the slot was read with that icon (or an alternative or label), amount and tradability, in order (`Good` or `NeedTradability`), and a slot set with no item as irrelevant, then `check: N of M slots set by hand read right` (`check_edits` in `native.rs`). The e2e tests over `CHECKED` captures do the same on the page after a re-run (`wrong_edits`).
- **Recording stops by itself at 5 GB** (`LIMIT`). A 3440x1440 screen that keeps changing makes about 2 GB a minute; a still screen sends no frames.
- **A re-run repeats exactly**: `replay` reads every slot at once (no time budget), and each frame is scanned only once the texts of the one before are back. Natively that is a read on the spot after each scan; on the page each frame waits until no line is out for OCR.
- **Replay on the page**: the upload input takes a `.hfcap`; the settings come from the start record and their controls are hidden. OCR workers start as for a live capture, and each input goes to the worker in place of a frame (`replay_wrapper`) with the texts that came back. After the last frame that frame is scanned again while texts still come back. The card then says `Replay finished, re-run on this build.` and the end record is on `window.__capture_reference`. Leaving the scanner page ends a replay.
- **Replay natively**: `cargo run --release --bin capture_replay -- <file.hfcap>` prints each hover once its last texts were in (the scans it was on screen, what it read, every vote, the slots beside it), the chests and the slot statuses. `pnpm scanner-suite` runs it over every `.hfcap` in `ignored/recordings` (as `cap-<name>`), so a capture that was fixed stays as a test. Native and wasm may differ on a score at a limit (other SIMD paths in the FFT and the resizer).
- **Finding out why something was not read**, with the same bin:
  - `--slot "Roster 0 0,2"` (as the keys of the end record's `edits` name a slot) prints every change to that slot and each hover that came up beside it. Start here: it gives the hover ids and scans to look at.
  - `--ocr` prints every line sent to be read with what it is for ("hover 212 description line 1") and its text; a line the scanner had seen before is not sent again, so it shows under its first hover only. `--from N --to M` keep it to those scans.
  - `--dump <folder>` writes the scanned frames (`scan-00849.png`) and the lines sent (`line-01440.png`, by id) of those scans.
  - `--reference <file>` writes the end record.
- **The native bins share what they print** (`describe`, `describe_chest`, `print_statuses` in `native.rs`). `hover_log` on the state, when set, collects every hover as it ends with its last texts in; nothing else reads it.
- **Not handled**: a capture whose window is partly off the frame panics on replay like it does live. Older captures (`HFCAP001` to `HFCAP004`) are not read; the local `HFCAP003` and `HFCAP004` ones were converted (`Pipeline tried.md`, "Recording").

## Conventions

- **Reference resolution is 1440p.** Slot positions, anchor offsets and window rectangles are constants in 1440p pixels, scaled by the game's UI height. Positions are kept as floats relative to the window origin; nothing is normalised to 0..1.
- **The capture size is the game resolution.** The share is the whole screen and the game is full screen, so nothing asks for it. The size is taken from the frames, not the track's settings: Chrome reported 3440x1920 for a 3440x1440 screen, and the frames then filled only the top of the buffer. The frame source holds back the first frame and the scanner is reserved at its size (`measure` in `FramePassing.ts`), so a start never reserves twice. A later frame of another size restarts the scanner at its size (the scan is lost). Test stills must be exactly a screen's size (the three that were a pixel or two short were padded at the right and bottom).
- **Forced 21:9 and brightness are each detected or given** (`Detected<T>` in `scanner_state.rs`: a value, `None` while not known, and whether the user gave it; `scan_settings` in `Resolution.ts` is the same shape). Both start on auto. The capture card has an `Aspect` select (Auto, 16:9, Forced 21:9) and a `Brightness` select (Auto, Manual with a 0 to 100 input), showing what was detected beside a setting on auto (`forced_21_9` and `brightness` in the scan result). Edits are a draft: an `Apply` button with a warning restarts the scanner, which clears the scan and the corrections; `Cancel` drops the draft. Not persisted; a replay takes them from the capture's start record.
- **Forced 21:9 is detected from letterbox bars** (`detect_21_9`, before anything else in `cropper`). Forced 21:9 draws the 64:27 picture with black bars where a 16:9 one would reach. A frame counts once over 20% of the 21:9 area's samples (one pixel in 4 each way) are above 10 in some channel; until then nothing is scanned (the game fading in). On that first frame it is 21:9 when both bands between the 21:9 and the 16:9 area are at least 95% samples at 10 or below in every channel, which leaves room for the cursor (nothing else is drawn there), and it is never looked at again. A capture wider than 2.1 is 21:9 without a look. Measured over every still: forced 21:9 bands are 99.9 to 100% black, 16:9 ones at most 65% even at setting 0; it also decided right on a frame of a still at 10% of its levels.
- **Manual brightness** is used from scan 0, so anchors are re-checked at their place and tooltips read before any button anchor is seen; no anchor's estimate replaces it.
- **UI height** is the height of the 16:9 (or 21:9) area the game renders into: the smaller of the capture height and width x 9/16 (or 27/64; the game's 21:9 is really 64:27, measured as 2560x1080 on a 2560-wide capture). The game draws over the whole capture width at any aspect (`render_width`, the right edge for `Bound::Render`); a native 3440x1440 screen (wider than 64:27) is drawn edge to edge, not as a centred 3413-wide picture. The scale factor is that height, rounded, over 1440. Rust derives both on every scan call from the capture size and forced 21:9.
- **Applying a settings change restarts the scanner** like a wipe does (worker terminated, state cleared, reserve again), because cached templates and remembered slots are scale-specific. The results table keeps its old rows until the first new result.
- **Pixels are RGBA** on both sides of the boundary, OCR jobs included: a job carries crops as captured. Only the strip the OCR worker makes of one is grey, one byte a pixel.
- **Fixed-position comparison is a colour distance, not a structural score.** It is the mean absolute RGB difference over the template without its outermost pixels, unshifted, reported as a confidence (1 - distance / 255). The pass limit is 0.9 unless the template carries its own required confidence, which only the page tabs do (0.8). Anchor search by template matching scores differently but uses the same rule: 0.9 unless the template carries a required confidence, which no anchor does yet. Because variants can both pass, slots take the best icon, never the first. `scanner_setup/scanner/icon_bench.py` still scores with the best of nine one-pixel shifts.
- **The slot limit is `SLOT_CONFIDENCE` (0.935)** in `slots/constants.rs`, which the decoys make safe (`Icon matching bench.md`). Tabs, anchors and whether a slot still looks the same keep 0.95 (`DEFAULT_CLOSE_ENOUGH_CONFIDENCE` in `close_enough.rs`). What a slot may also be (the alternatives) keeps 0.95, or the other rarity of the same art comes in. A lit or half covered look passes more often at 0.935, so the slot's own number is read under the cursor more; the tooltip's amount is what counts there.
- **The game scales its UI continuously.** Nothing is snapped to whole pixels and no step is rounded: matched positions are spread flat over the fraction of a pixel, and the distance between any two anchors is the same in UI units at every height. So a resolution-dependent offset is ours, not the game's.
- **Slot pitch was measured on a 1440p capture** (69.75 px), and holds to 0.006 UI per step across all native heights. The grid is the same in every window except that roster storage's starts about 0.9 px further left. A pitch error accumulates across the grid, so re-measure against a native capture rather than nudging it by eye.
- **One rectangle type, which knows its space** (`Rect` in `image_utils/common.rs`). A rectangle is in `Space::Ui` (1440p UI units: constants, base template offsets, bounds) or `Space::Screen(ui_height)` (screen pixels: scaled templates, matches, crops). `scaled` only goes from the first to the second, `get_offset` wants both in one space, and `crop_buffer` (a method of the state) wants screen pixels at the current UI height; each asserts. Position and size stay fractional, and `pixel_size()` is the only place a size is rounded. A scaled template's offset and a match are stored at whole pixel size (`whole_pixels`). Roots (an anchor's, a window's origin) are plain points and carry no space. `Rect` has no serde: the config file's offset and a slot image's go through `WireRect` in `setup.rs`.
- **Fixed-position comparison needs identical dimensions, and panics without.** `confidence` asserts that template and crop have the same pixel size and space.
- **The frame buffer is sized once**, at capture start, and freed when the worker is terminated. JS must rebuild its view of wasm memory every frame, since memory growth invalidates old views.
- **Brightness is normalised.** The in-game brightness setting changes pixel values, so observed crops are mapped to a fixed reference brightness before comparison. Stored templates are already normalised. See `Config and calibration.md`. A crop comes out of `crop_buffer` as captured and is normalised by whoever made it (`normalize_brightness`, once: nothing remembers that it was done); `close_enough` and `confidence` take both sides as they are. The table for a setting (`brightness_lut`) is kept from one call to the next and made again only when the estimate moves, in the scanner and in the OCR workers alike. Left as captured on purpose: a slot's number crop, its display image, the area an anchor is searched in, and the patch an anchor's brightness is read from.
- **The brightness estimate is an average that only gets better.** An anchor variant gives its own estimate when it is found: the mean of the matched patch through a curve fitted for that variant. One that matched the wrong thing gives nonsense. The setting does not change during a session, so the estimate used is the average over the most anchors ever found together (or as many again), and it stays when some of them are lost. An anchor only counts once it has passed its re-check on a later scan, and no longer counts when it fails one. Until any has, the estimate is the first anchor's own. `tooltip_test` prints each change and each anchor's own estimate to stderr.
- **A window fading in must not fix the estimate.** The storage layout fades in over about 20 frames and its anchors match from the first dim one (the search score ignores brightness), reading 0 and then rising. So an anchor's estimate is taken again from the frame at every re-check it passes, and when no anchor passes, the count goes back to none so the next anchor found sets the estimate. The cost: when every anchor is lost (storage closed) the next match, right or wrong, sets the estimate, as at the start of a session.
- **Which anchors tell the brightness.** The buttons do (sort, search, Storage): 5 in the storage layout, 2 on the lone inventory. The storage windows' icon groups do not: thin icons are drawn anew at each resolution and their mean differs by several settings between resolutions. The average is within about a setting of the truth at 1080p.
- **What the setting is: a display gamma.** A value seen at setting 50 becomes `value ^ ((62.6 + 50) / (62.6 + setting))` at another setting, with values as 0 to 1. Normalising to 50 is the inverse, and that is the whole model (`brightness.rs`): one number, no gain. It reads as a gamma that rises in a straight line with the setting; only the ratio 62.6 of that line's offset to its slope can be told from captures. Black and white are fixed points of a power law. It fits opaque icon pixels to a fraction of a level on average.
- **The gamma is applied to what is drawn, before it is blended.** Pixels that share a value at 50 do not land on one value elsewhere. White glyphs are the clear case: white stays white and only the icon under a soft edge changes, so the number crop is not normalised like the rest (below), and tooltip text edges come out a few percent too dark or too bright when normalised per pixel. What shows through a nearly opaque panel is the same thing: the tooltip body is brighter than its title bar at setting 0 and darker from 10 up.
- **Capture stays at native resolution.** The quantity digits need full resolution.
- **Slot numbers are separated from the icon with a compositing model** (`ocr/number.rs`). The game's brightness setting changes the icon but not the number drawn over it (digit pixels are identical across all 21 settings). So the number crop is used as captured, never normalised, and the expected background is the matched icon's template moved to the on-screen brightness.
  - The template is lined up to a quarter pixel on the icon area below the number, which nothing covers (the number hides most of its own strip): a single quarter-pixel step either way, nine samples.
  - Each pixel is then explained as white digit over shadowed background, which gives how much white the template cannot account for and how much the template had to be darkened. A white pixel is a digit if the template cannot explain it, or if it has the number's dark shadow within reach on both sides (digits over a white part of the icon). Nothing else survives, so icon highlights are gone. The shadow test has to stay: nothing else vouches for a digit over a white part of an icon.
  - A third test goes by colour (`alpha_by_colour`): shading keeps a background's hue and white washes it out, so how grey a pixel is over a coloured part of the icon says how much of it is digit, however bright that part is. It only speaks where all nine template neighbours are coloured (channel spread of 40 or more). It is for thin strokes over pale coloured icons, which the first test explains as half white over the icon.
  - A fourth rule joins strokes: a pixel short of the limit (`low_alpha`, 0.3 against 0.55) still counts where it touches a digit pixel.
  - After that: blobs of a few pixels are removed, the empty black left of the number is cut off with a small margin (the recogniser is touchy about it: 2 to 4 px at 1080p works, 6 to 8 px is much worse than no crop), and the strip is resized to 64 px, white on black. Numbers are not inverted, although tooltip text is and reads better that way.
- `cargo run --release --bin slot_scores -- <still>...` prints, for every slot that looks like something, the four icons and decoys it is closest to, each with its score, its score with the overlays found on it left out and its place in the shortlist's order, whatever the limits. `DUMP=<folder>` also writes each slot as seen next to its closest icon.
- **Working on the number clean-up.** One function makes the strip (`number_strip` in `ocr/number.rs`, with a `NumberParams`), and two bins sit on it:
  - `number_bench` re-reads every slot number the scanner asks for, under each entry of its `variants()` list and with both alphabets, from stills or a piped recording; `scanner_setup/tooltips/number_bench.py` scores the output. Stills of one scene at many brightness settings are scored against the read most agree on, recordings against the tooltip amounts, per read and per slot (last read, and the vote of five). Add a variant to the list to try something.
  - `number_probe` writes every stage of one slot's clean-up as images each time that slot is read (captured crop, expected background, white by fit, white by colour, shadow, mask, strip), and `scanner_setup/tooltips/number_stages.py` stacks them into one picture per read.
  - Older: `number_dump` and `number_test` dump number and icon crops from stills and score pre-processing against hand labels (`scanner_setup/tooltips/number_labels`). Those labels are from before the chest table and no longer line up with a fresh dump.
- **OCR** uses the `ocrs` / `rten` crates with only the recognition model, on a preprocessed single line, 64 px tall. Text detection is skipped because the number's position is known.
